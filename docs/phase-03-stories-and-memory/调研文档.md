## 1. 结论摘要

1. **没有找到与 Momoly 目标完全同款的开源项目**：现有项目分别覆盖"约会成品"（heartmorrow）或"互动叙事框架"（covel），但没有同时具备"聊天 App 内邀约 → 有状态场景 → 结算回聊天"的完整组合。
2. **最接近的约会成品是 heartmorrow（Unlicense）**：选角色/地点 → 流式约会对话 → 独立结算 pass 生成关系与记忆；缺角色邀约、选项分支与聊天回写。
3. **最接近的互动叙事框架是 covel（MIT）**：Stage 视觉小说模式（背景/立绘/选项 overlay）+ 世界时间 + 隐藏剧情事件 + 按 NPC 好感；它是创作工具，不是聊天 App，无邀约回写闭环。
4. **技术路线取"预写 beat 骨架 + LLM 填充 + 世界书设定注入"的组合**（②+①+④，见 §3.7）：beat 负责流程与节奏，LLM 只负责表达，世界书负责设定层，避免纯 LLM 现编导致的状态漂移。
5. **事件选择借用 Yarn Spinner 的 storylet/saliency 思想**：`when` 条件最具体者优先，同级取"最久未出现 + 随机"；官方教训是可验证的：**条件求值必须纯函数，状态更新只能发生在选中之后**。
6. **结算与信息隔离有成熟证据**：heartmorrow 独立结构化结算 pass（失败不改存档、空场不计数）；loreweaver 的"叙事→账本对账"与 `project()` 信息隔离；TRPG-AI-DM 的 `discovered/visible` 与 covel 的"条件不满足不进 prompt"——比在提示词里叮嘱"别剧透"可靠。
7. **许可上安全**：Momoly 为 AGPL-3.0；AGPL 项目（SillyTavern、Shikigami、Extension-Idle、KoboldAI）只参考设计不复制代码；MIT/Apache 项目（Yarn Spinner、Ink、BRING、covel、heartmorrow 的 Unlicense）可参考实现。所有引用结论来自 2026-10-31 调研，细节见 §7 核验说明。

## 3. 关键机制与证据

### 3.1 邀约状态机与到点/补算

- **证据**：旧 design/04 给出完整状态机（用户发起/角色发起、`PENDING_CHARACTER`/`PENDING_USER`/`SCHEDULED`/`ONGOING`/`FINISHED`/`MISSED`/`CANCELLED`、改约、拒绝冷却）；BRING 用 Director tick 推进日程 beat；heartmorrow 的约会由玩家发起、角色会发短信但无"角色邀约→确认时间地点"。
- **对本阶段含义**：核心状态是"约定存在 → 赴约进行 → 故事结束"；到点提醒、错过补算依赖通知与主动消息，属阶段 4，不塞进阶段 3 验收。
- **证据强度**：旧设计为内部方案（非外部证据）；BRING/heartmorrow 机制来自 README/文档，已核验仓库与许可，未运行验证。

### 3.2 beat / storylet 的 saliency 选择

- **证据**：Yarn Spinner 的 storylet + saliency——候选事件按 `when` 条件与复杂度评分选"最具体"者，默认"最久未出现 + 随机"；`when: once` 防重复；官方博文强调条件求值期间不得修改状态。
- **旧方案算法**：过滤适用地点 → 过滤 `when` 为真 → 过滤 once/cooldown → 取非概率谓词数与 priority 组成复杂度 → 最高复杂度池 → 排除最近窗口使用过者 → `lastTurn` 最早并列组内随机。
- **对本阶段含义**：beat 选择放纯 domain 层（随机源可注入、可重放），使"发生什么"可测试、可复现；LLM 只拿到导演指令与状态事实，不决定事件表。

### 3.3 选项生成与解析容错

- **证据**：旧 design/04 的 `OptionParser` 容错表——块合法/2–4 项/类型合法则采用；JSON 非法或截断时行内正则兜底或退化为"仅自由输入"；超限截断、非法类型改默认；正文为空用地点摘要兜底。
- **补充证据**：heartmorrow 用 intent chips（Flirt/Tease/Open Up/Reassure/Apologize）表达"怎么说"，与"做什么"正交，误读会反噬——说明选项结构可以带"方式"维度，但当前需求未确认该扩展。
- **对本阶段含义**：解析失败不能报错打断故事；无选项时自由输入必须仍可用。当前需求只要求"选项 + 自由输入"，具体输出格式属设计细节。

### 3.4 结算回写与独立结算 pass

- **证据**：heartmorrow 把"约会对话"与"结束结算"拆成两次调用，独立校验 pass 把整场转成关系/心情/记忆，校验失败不改存档，"开始约会却一句话没说"不计数；loreweaver 用小模型 Scribe 每回合把叙事对账为状态，防止"叙事推进三天、账本不动"。
- **旧方案**：`OutingSummary`（title/place/time/highlights/promiseNext/memoryLine/endReason）由单独非流式调用产出，失败模板兜底，回写 1–3 条 assistant 消息 + 回忆卡，幂等去重。
- **对本阶段含义**：结束摘要应"只从已提交回合提取"，空场不结算、不产生记忆；回写聊天的形态受当前"线上纯消息"约束，**回忆卡是否允许需产品确认**（见 [需求文档 §7.2](需求文档.md)）。

### 3.5 信息隔离与知情范围

- **证据**：loreweaver 的 `project()` 把角色不该知道的信息从投影中排除；TRPG-AI-DM 用 `discovered/visible` 区分已发现/可见；covel 的隐藏剧情事件在条件满足前**不进 prompt、不进工具、不进公开 API**。ai-murder-mystery 用"生成→批评→修订"三阶段防泄露。
- **对本阶段含义**：P3-09（周宁不知情）不能只靠提示词叮嘱"不要提借书"；应在数据层按角色隔离记忆，生成时只注入该角色已知事实。这也解释了设计文档把记忆按 `charFile` 隔离的原因。

### 3.6 场景页面形态与中断恢复

- **证据**：covel 的 Stage 模式（场景背景、立绘、打字机对白、选项 overlay），地点无专属图时回退世界图；heartmorrow 的约会会话 server-truth、刷新/切标签自动恢复；旧 design/04 场景页线框（场景头 + 消息区 + 选项区 + 输入区）与"每回合原子落盘"。
- **对本阶段含义**：故事页可复用现有消息渲染与贴底滚动规则，但旁白需要独立渲染、选项独立组件；恢复靠"每回合落盘 + 幂等 turnId"，离开页面只暂停不结束。

### 3.7 技术路线对比（旧调研结论）

| 路线 | 代表 | 状态存法 | 结论 |
| --- | --- | --- | --- |
| ① 纯 LLM 生成（历史即状态） | KoboldAI Adventure、聊天客户端剧情模式 | 历史 + 摘要 | 表达层可用，不承担流程 |
| ② 预写 beat 骨架 + LLM 填充 | BRING、旧 design/04 | 显式 SceneState + 事件表，序列化 JSON | **本阶段主路线**（纯 domain 解释器） |
| ③ 脚本引擎（Ink/Yarn/Twine/Ren'Py） | Ink、inkjs、Yarn Spinner | 引擎保证状态机与存档 | P2 可选；本阶段不引入运行时 |
| ④ 世界书/关键词触发 | ST 世界书、现有 `activateWorldInfo` | 条目 + 激活状态 | **设定层**，不能表达流程与分支 |

## 4. 历史方案与差异

历史方案指 2026-10-31 的宿主调研 design/04、设计说明 §3.3、调研报告 §3.4。**与当前五阶段计划冲突时以当前产品需求与阶段计划为准**；下表差异不是需求变更，而是收敛后的取舍记录。

| 维度 | 历史方案（2026-10-31） | 当前五阶段计划 / 需求 | 处理 |
| --- | --- | --- | --- |
| 地点来源 | 内置 **10 个地点**（咖啡馆、餐厅、电影院、公园、海边、书店、小酒馆、天台夜景、游乐园、美术馆）+ 自定义地点，`assets/places.json`，带 tags/activities/beatSets | 地点来自世界书（阶段 2 接入），新地点由 agent 生成（阶段 5）；未确认是否保留内置地点库 | 以世界书为事实来源；内置地点库是否作为初始内容待调研 |
| 邀约发起 | 角色主动（距上次 ≥3 天、概率 25%、每日 1 次、冷却 24/48h）+ 用户"邀请 TA 出门"按钮 + 到点提醒 + 错过补算 | 阶段 3 只确认"聊天出现赴约按钮 → 用户点击 → 移动 → 故事"；角色主动邀约、提醒、补算属阶段 4 主动联系 | 阶段 3 先做最小状态集；角色发起是否纳入阶段 3 待产品确认 |
| 状态机 | 完整 `PENDING_CHARACTER`/`PENDING_USER`/`SCHEDULED`/`ONGOING`/`FINISHED`/`MISSED`/`CANCELLED`，含改约/拒绝理由 | 需求未定义状态机；只要求禁止快穿、结束/继续、状态一致 | 设计文档给最小状态集草案，其余待确认 |
| 多人参与 | 首版单角色，`SceneState.characters` 仅预留，多角色 P2（对应旧 C9） | 阶段 3 **必须完成**多人共同参与与知情范围（P3-05、P3-09） | 本阶段补多人；生成方案待调研 |
| 数据模型与存储 | 旧 `OutingPlan`（邀约）+ Scene JSON（每场一个，含 `SceneState`/messages/summary）+ 可重建索引，备份 `FORMAT_VERSION` 4→5、独立 `Section`、出行记录页 | 计划 JSON；已取消独立保存/恢复/备份迁移模块与备份恢复验收 | 保留 JSON 与原子写；不做独立备份/迁移验收 |
| 消息类型 | 全部走 `messages.dataJson` 的嵌套保留键 `momoly`（`kind=invite/outing_summary/system/proactive`），前端组装前剥离，重答保留，不迁移 Room | 未确认沿用该键；阶段 3 回写形态未定 | 沿用与否待确认；不得把旁白写进消息正文 |
| 结算回写 | `OutingSummary` + 回写 1–3 条 assistant 消息 + 回忆卡 + `memoryLine` + 好感/关系 + 出行记录 | 需求只确认"线下经历影响后续聊天"；线上只显示角色实际发来的消息正文（P3-08） | 摘要写记忆（定）；回写消息条数与回忆卡待确认；好感数值未确认 |
| 关系数值 | `affinity` 0–100 隐藏、`mood`、`promiseNext`、多结局 | 当前需求未包含关系数值/结局系统 | 不实现，只有"关系变化影响后续"的定性要求 |
| 选项结构 | 同次流式生成尾部 `<<OPTIONS>>` 块，2–4 项、type 白名单、解析容错 | 需求只要求选项 + 自由输入；格式未规定 | 归设计实现，不写进需求 |
| 场景内时间 | `elapsedMin` 每回合 +10、时长取地点默认值（如咖啡馆 90 分钟）、`turn ≥ 60` 安全上限 | 需求未规定故事内时间推进与时长 | 开放问题，与阶段 2 时间轴统一后再定 |
| 场景画面 | 场景头 + 背景渐变卡 + 天气/时长 chip；covel 式背景/立绘 | 需求要求场景叙述、动作、对话、选项与自由输入；未要求立绘/背景图 | 立绘/背景为可选增强，不进入验收 |
| 快穿 | 旧方案未讨论"故事期间的世界切换限制"（其范围是邀约/场景本身，不含与快穿的交互） | 当前明确：故事进行期间禁止快穿，必须先结束（单/多人都适用） | 新增硬约束，设计需持久化状态门闩 |
| 群聊基础 | ST 群聊发言顺序策略（Manual/Natural Order/talkativeness/List/Pooled）可参考，Momoly 未实现群聊 | 多人同场需在本阶段内落地 | 发言顺序策略待调研，首版先保"可辨认" |
