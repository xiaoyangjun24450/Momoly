# 阶段 5 设计文档：地点拓展与整体验收

同阶段：[需求文档](需求文档.md) · [调研文档](调研文档.md)　｜　[文档总览](../README.md)　｜　前置 [阶段 4](../phase-04-proactive-messages/需求文档.md)

## 1. 目标与约束

本设计把 agent 生成的新地点接入既有世界、出行、故事和记忆链路，并安排五阶段整体验收。本文只写实现方式与当前状态；做什么、验收标准见 [需求文档](需求文档.md)。

| 类别 | 约束 | 依据 |
| --- | --- | --- |
| 复用生成链路 | 地点生成复用 `:domain:generation` 的 `PromptBuilder`、世界书激活 `activateWorldInfo` 与 `GenerationEngine`，不复制第二套 Prompt 装配 | [CLAUDE.md](../../CLAUDE.md)「模型调用与 Prompt 装配」 |
| 模块方向 | `app → feature → domain/core`，数据实现位于 `data:*`；`:domain:*` 只依赖 `:core:model` 与协程 | CLAUDE.md「架构」 |
| 数据写入 | 生成结果写入当前世界的地点数据，最终形态待调研（世界书条目或独立地点数据） | 需求 §4 C1/C2；调研文档 §6 |
| 不写角色卡 | 不把地点、路线等运行时数据写进角色卡 JSON，避免破坏 SillyTavern 兼容导出 | CLAUDE.md「SillyTavern 兼容性」；历史 design/04 §2.4 |
| 不加数据库迁移 | 本阶段不新增备份/迁移模块；若确需 Room 变更，按 v9 基线起显式迁移与快照铁律，计划中不引入 | [文档总览](../README.md) §2；CLAUDE.md「聊天记录」 |
| UI 导航 | 沿用单 Activity + `ChatDestination` 返回栈，新增页面 = 枚举值 + `ChatDestinationHost` 分支 | CLAUDE.md「架构」 |

## 2. 模块归属与依赖方向

| 能力 | 建议落位 | 职责 | 依赖 | 状态 |
| --- | --- | --- | --- | --- |
| 地点生成编排（请求、上下文组装、结构化输出、重试） | `app` 编排层；或新 `:feature:location`（待定） | 调用生成、校验、落库、刷新列表 | `:domain:generation`、`data:worldbook` | 计划 |
| 生成上下文与 Prompt | `:domain:generation`（复用 `PromptBuilder`） | 注入当前世界设定、已有地点与出行信息 | `:core:model` | 复用现有，扩展点待定 |
| 生成结果校验与合并规则 | 纯逻辑入新 `:domain:location`（待定） | schema 校验、同名判定、路线引用校验、合并决策 | `:core:model` | 待定 |
| 地点与路线的持久化 | `data:worldbook`（现有 JSON 文件仓储）或新 `:data:location`（待定） | 原子写入、同名保留旧条目、按世界隔离 | 现有仓储接口 | 待定 |
| 出行解析（方式/耗时/路线） | 阶段 2 出行模块（模块 4） | 解析地点间路线，返回可选出行方式与耗时 | 地点数据 | 阶段 2 交付 |
| 角色日程与移动 | 阶段 2/3 模块（模块 5） | 角色按日程和路线移动，禁止瞬移 | 时间、地点数据 | 阶段 2/3 交付 |
| 新地点线下故事与记忆 | 阶段 3 模块（模块 7、8） | 复用既有故事流程，故事记忆回写原会话 | 阶段 3 接口 | 阶段 3 交付 |
| 地点拓展入口与结果展示 | `app/ui`（待定具体页面） | 入口、生成中状态、结果与"哪些被添加"的说明 | `ChatDestination` 返回栈 | 计划 |
| 整体回归与验收记录 | 无新模块 | 按需求文档用例在真机执行并归档 | 全部模块 | 计划 |

依赖方向（沿用现有约束）：

```text
app（MainActivity / 页面 / 手工装配 AppContainer）
  → :feature:*（Controller、ViewModel、UDF）
  → :domain:generation（PromptBuilder / GenerationEngine / MacroEngine / 世界书激活）
  → :core:model
data:*（worldbook / chat / settings）← app 中的 Android 数据源与仓储实现
```

待定项与依据：调研报告曾建议新增纯 JVM `:domain:scene`/`:data:scene` 与独立 JSON 存储（历史方案），但当前产品需求要求地点写入世界书并沿用阶段 2 的出行表达；因此新校验逻辑是否可以独立成 `:domain:location`、持久化是否落到 `data:worldbook`，需在阶段 2 出行数据结构定稿后决定。无论落在哪，领域校验保持纯 Kotlin，不依赖 Android，`checkArchitecture` 作为发布门槛。

## 3. 数据模型与存储

### 3.1 生成任务与结果（草案，字段待调研定稿）

```json
{
  "request": {
    "worldId": "world:campus",
    "userRequest": "在校园里增加一家靠近图书馆的咖啡馆"
  },
  "context": {
    "existingPlaces": [{ "name": "图书馆", "aliases": ["library"] }],
    "travelModes": ["walk", "bike"]
  },
  "result": {
    "place": { "name": "咖啡馆", "scene": "图书馆东侧的临街小店…", "aliases": [] },
    "connections": [
      { "from": "图书馆", "to": "咖啡馆",
        "modes": [{ "mode": "walk", "durationGameMinutes": 6 }] }
    ]
  }
}
```

示例只表达"地点 + 连接 + 方式 + 耗时"的关系，不作为字段名、单位或方式枚举的定稿。定稿前以阶段 2 已接入的世界书表达为唯一事实源，生成侧只负责产出同构数据。

### 3.2 校验规则（计划）

| 规则 | 失败处理 | 依据 |
| --- | --- | --- |
| 地点名称、场景描述非空 | 拒绝写入并提示，允许重试 | 需求 §3.1 |
| 至少一条连接已有地点的出行信息，含方式与耗时 | 拒绝写入；仅场景描写不算可用地点 | 需求 §4 C1 |
| 连接目标必须能在当前世界解析到已有地点 | 拒绝或要求重新生成 | 需求 §3.1 |
| 出行方式属于阶段 2 已接入的枚举，耗时为合理正整数 | 拒绝或按既定默认值处理（待定） | 需求 §7.2 |
| 不得引用其他世界的地点或设定 | 拒绝写入，不影响其他世界 | 需求 §4 C5 |
| 同名条目按"保留旧条目"处理，不覆盖 | 保留旧内容，并在结果中说明未添加项 | 需求 §4 C2/C3 |

校验范围和严格程度（拒绝、提示、可重试的边界）待调研；不能用"字段齐全"替代线上纯消息与流程验收。

### 3.3 写入与合并规则（计划）

| 场景 | 行为 |
| --- | --- |
| 新地点名称不与当前世界任何条目同名 | 追加新地点条目及其连接信息 |
| 名称与已有条目同名 | 保留旧条目内容；不覆盖、不合并正文；结果提示哪些内容被保留 |
| 新增路线与已有路线重复 | 保留已有路线；新数据不覆盖 |
| 写入其他世界 | 禁止；地点只写入发起请求时的当前世界 |
| 写入失败/进程中断 | 原子写入（临时文件 + 重命名）；失败回滚到写入前状态 |
| 重复提交同一生成任务 | 幂等键（世界 + 请求摘要或生成任务 id）去重，不重复追加 |

具体存储字段、文件位置和条目结构待调研（候选：写入现有世界书 JSON 条目 / 独立地点数据文件再投影到世界书 / 两者兼有），见 §9 开放问题 1。

### 3.4 与阶段 2 出行模块的接口（待定）

```text
TravelResolver.resolve(worldId, fromPlaceKey, toPlaceKey)
  -> List<TravelOption>            // { mode, durationGameMinutes, source }
```

- 解析器由阶段 2 交付；本阶段只新增"生成地点→已有地点"的边，不另写解析逻辑，避免两份格式漂移。
- 待定项：地点键空间（条目名/程序 id/别名）、路线方向性与返程、耗时单位、方式枚举、默认耗时缺失时的处理。

### 3.5 与故事、记忆的接口

- 前往新地点后进入阶段 3 既有故事流程，故事场景使用新地点快照；不新增故事数据格式。
- 故事结束的记忆回写沿用既有聊天消息写入入口（同一角色同一会话），不新建会话、不改写历史消息正文。
- 进入新地点故事前必须满足角色位置与日程条件，由阶段 2/3 既有校验保证，阶段 5 不绕过。

## 4. 接口与关键流程

### 4.1 主流程

```text
用户在当前世界发起地点拓展请求
→ 组装上下文（当前世界设定、已有地点与出行信息）
→ GenerationEngine 生成（结构化输出；流式展示与否待定）
→ 解析并校验（失败：提示 + 重试/放弃，不写入）
→ 合并写入当前世界（同名保留旧条目、其他世界不受影响、原子写）
→ 刷新地点列表与可用路线
→ 用户选择路线 → 阶段 2 出行（路上 / 推进时间 / 到达）
→ 角色按日程移动 → 阶段 3 线下故事 → 记忆回写聊天
→ 阶段 4 通知与五阶段整体回归
```

### 4.2 冲突与回滚

| 情况 | 处理 |
| --- | --- |
| 生成内容与已有条目同名 | 保留旧条目，结果说明未添加部分；不静默覆盖 |
| 生成内容缺连接/方式/耗时 | 视为无效结果，不写入、不显示为可前往地点 |
| 同一世界并发两次生成 | 按世界串行或幂等键去重，避免交叉写入 |
| 生成过程中切换世界 | 写入目标固定为发起时的世界；切世界后不得写入新世界（待定：是否直接取消任务） |
| 写入中途失败 | 原子写 + 回滚，失败不留下半条地点记录 |
| 进入出行时路线已失效 | 回到地点列表并提示重新选择（待定） |

### 4.3 发布验收流程

1. 确认待验收代码已提交，构建可安装版本并记录构建标识；在目标设备安装，记录设备与运行场景，准备统一角色卡、世界书与验收素材。
2. 按 [需求文档](需求文档.md) §5 的 P5-01～P5-09 逐项执行，留存截图与录屏；连续行为必须录屏。
3. 回归前四阶段关键路径（导入、聊天、时间、出行、故事、记忆、冻结、通知）。
4. 汇总各用例实际结果与未解决问题；未通过项保持"未通过"。
5. 是否需要打 tag/构建正式发布版本，按 [CLAUDE.md](../../CLAUDE.md)「发布版本」约定执行，本阶段不新增发布流程。

## 8. 风险、限制与技术债

| 风险/限制 | 影响 | 缓解/处理 |
| --- | --- | --- |
| 生成结果不稳定或编造设定 | 可能生成与世界观冲突的地点 | 上下文注入现有地点与设定；校验失败不写入，允许重试 |
| 耗时数值由模型给出 | 数值可能不合理，但验收不要求固定分钟数 | 设基本合理性校验（正整数、上限待定）；以实际保存数据验收 |
| 世界书表达与存储未定 | 数据模型可能返工，影响合并与出行接入 | T1 先定稿再实现；设计保留候选方案 |
| 同名判定粒度未定 | P5-03 合并结果可能解释不清 | 验收前明确条目名/地点名/别名口径 |
| 路线方向性与返程缺失 | 前往新地点后无法返回 | 生成结果要求足够连接信息；返程由素材补充或在生成时校验（待定） |
| 与阶段 2 解析器出现两套格式 | 格式漂移、地点不可用 | 生成侧只产出同构数据，解析只保留一份 |
| 并发写入与切换世界 | 地点写错世界或重复 | 按世界串行/幂等；写入目标固定 |
| 生成 token 成本与延迟 | 体验变慢 | 精简上下文；是否流式展示待定 |
| 无地点编辑 UI | 生成结果不理想时用户难以修正 | 本阶段不做编辑器；记录为后续需求候选 |

技术债：阶段 2-5 的出行数据表达、故事记忆接口均未定稿，本设计中的接口为草案；新地点持久化若最终落在世界书，需要处理 ST 导出兼容与合并展示，若落在独立文件则需处理与阶段 2 解析的同步。

## 9. 开放问题

1. 新地点最终持久化位置：世界书条目、独立地点数据，还是两者兼顾？依据是什么？（影响合并与导出）
2. 生成结果 schema 与严格度：必填哪些字段？不合法时拒绝、提示还是降级？
3. 出行方式枚举、耗时单位、默认值由阶段 2 确定后，生成侧如何复用而不复制？
4. 路线是否要求双向、返程如何生成或校验？
5. 生成结果是否需要用户确认或允许编辑后再写入？生成失败/信息不全时是否允许保存为"草稿地点"暂不可前往？
6. 同名判定用条目名、地点名还是别名集合？
7. 生成过程中切换世界是取消任务还是固定写入原世界？
8. 验收记录与构建标识的归档规范（是否入文档索引、是否要求正式 tag）？
