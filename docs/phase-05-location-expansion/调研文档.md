# 阶段 5 调研文档：地点拓展与整体验收

同阶段：[需求文档](需求文档.md) · [设计文档](设计文档.md)　｜　[文档总览](../README.md)　｜　前置 [阶段 4](../phase-04-proactive-messages/需求文档.md)

## 1. 结论摘要

1. GitHub 上没有"微信式 UI + SillyTavern 角色卡 + 本地主动消息 + 邀约出门"四件套齐全的开源项目；最接近的现成产品是 [Muse](https://github.com/Zer0Qing/Muse)（差出门），玩法面最全的是 [Float](https://github.com/Jiuguo9791/Float)（无"邀约→时间地点→场景循环→回写"闭环，且依赖个人云）。Momoly 的组合仍是空位（宿主旧调研 notes/08 §3、同类项目对标 §0，见 §7）。
2. 地点与场景生成可直接借鉴的机制集中在四个工程：[Veranima](https://github.com/KamisugiMizuki/veranima-companion) 的"地点池 + DayRoute + CurrentScene + 离线 reconcile"、[BRING](https://github.com/Eva-E1/BRING) 的 Director 分层实体、[heartmorrow](https://github.com/HMDSimDev/heartmorrow) 的"结构化结算独立 pass、校验失败不落库"、[loreweaver](https://github.com/1A7432/loreweaver) 的"叙事→账本对账"。它们都是 Python/Web 栈，许可允许只借设计（Veranima/heartmorrow/loreweaver 均为 MIT/Unlicense 系）。
3. 当前阶段 5 的地点来源与历史调研不同：历史方案是"内置 10 个地点 + 自定义地点"（design/04 §2），当前权威需求是"世界书提供固定地点 + agent 生成新地点"（[需求文档](需求文档.md) §3）；历史方案只作机制参考，不能直接作为验收依据。
4. 历史调研已给出 Place/Scene/OutingPlan/Beat 的字段草案与"独立 JSON 存储、结束回写 1-3 条消息"的路线；当前阶段只复用其中与"地点生成→合并→出行→故事"相关的思路，邀约状态机、beat 规则库、好感数值等未纳入当前计划。
5. 生成内容的最大风险不是文笔，而是结构不可用：只有场景描写、没有与已有地点的连接/方式/耗时的结果不能成为可用地点。参考 heartmorrow 的"独立校验 pass"与 loreweaver 的"叙事与账本分离"，应先定 schema 与校验，再谈生成内容质量（[设计文档](设计文档.md) §3.2）。
6. 许可红线：本阶段参考项目多为 AGPL/GPL 系或无可核实 LICENSE；Momoly 本身为 AGPL-3.0，引用代码必须保留义务，但设计/机制可借鉴，代码与素材不可直接搬（§5）。

### 3.4 世界书作为设定层

- SillyTavern 世界书与 Momoly 既有 `activateWorldInfo` 提供地点、场景描述与关键词注入，零新依赖（调研报告 §3.4，宿主旧调研）。
- 历史设计明确"场景不改世界书文件，而是用锚点消息命中条目"（design/04 §2.4）；当前需求则要求生成地点写入当前世界并沿用同名保留旧条目规则（[需求文档](需求文档.md) §4），两者的合并与写入位置需在阶段 2 表达定稿后确认，属于待调研项。
- 结论：世界书可承担"地点设定"的持久化，但是否同时承载"路线/耗时"的结构化数据尚未有依据，不能直接照搬历史方案。

### 3.5 证据强度与缺口

- 以上项目均只读过 README/设计文档，未下载运行；"待核实"项不用于下结论。
- 没有找到直接回答"如何校验 agent 生成的地点及其与已有地点连接"的一手资料；该问题只能结合当前世界书表达自定，属待调研问题（§6）。
- 历史 design/04 的 beat/选项/总结机制有作者侧设计证据，但与当前阶段 5 边界无关，只作背景。

### 4.2 旧数据模型要点（历史）

- `OutingPlan`：id/sessionId/charFile、发起方与来源、地点快照、约定时间、活动、状态机（PENDING/ SCHEDULED/ONGOING/FINISHED/MISSED 等）、提醒与冷却。
- `SceneState`：turn/turnId、elapsedMin、act、flags/stateFacts、affinity/mood、选项、beatHistory、rngSeed。
- `Beat`：when 谓词、priority、once/cooldown、directive、options、effects。
- `OutingSummary`：地点/时间/时长、highlights、promiseNext、mood、affinityDelta、memoryLine；结束回写主会话 1-3 条消息。
- 存储：`filesDir/scenes/*.json` 每场一个 + `index.json`，`places_custom.json` 存自定义地点，纳入备份。

### 4.3 当前方案与历史方案差异

| 维度 | 历史方案（2026-10-31） | 当前权威方案 | 处理 |
| --- | --- | --- | --- |
| 地点来源 | 内置 10 个 `assets/places.json` + 自定义地点；不依赖角色卡解析（需求说明 §8.3 A3，默认假设） | 世界书提供固定地点；阶段 5 由 agent 生成新地点（产品需求 §2.4） | 以当前需求为准；旧地点库只作标签/场景提示参考 |
| 新地点引入方式 | 用户自定义（名称+标签） | agent 根据用户请求与世界设定生成，必须包含出行信息 | 旧自定义地点 UI 不纳入本阶段 |
| 地点字段 | Place 固定字段（tags/activities/beatSets 等） | 字段结构待调研，不预设 | 旧字段只作候选，不写入当前需求 |
| 出行/路线 | 设计未覆盖"新地点→已有地点"的移动耗时；耗时取地点默认值 | 生成结果必须含连接已有地点的出行方式与游戏内耗时；沿用世界书耗时 | 当前要求更严；直接约束可用性 |
| 存储与备份 | scenes/、places_custom.json 纳入备份 | 写入当前世界；正常业务连续性不涉及备份迁移 | 以当前为准；旧备份任务已取消 |
| 邀约流程 | OutingPlan 状态机 + 邀约卡 + 提醒 + 错过补算 + 冷却 | 阶段 3 赴约/前往按钮 + 出行 + 故事；本阶段只复用 | 旧邀约系统不属当前计划 |
| 场景数据 | Scene JSON + Beat 规则库 + 选项解析 | 阶段 3 定义；阶段 5 不新增格式 | 以阶段 3 文档为准 |
| 结束结算 | 结构化 OutingSummary + 模板兜底 + 回写 1-3 条消息 | 阶段 3 记忆回写；本阶段验收 | 借鉴"先校验后落库" |
| 验收 | design/04 的分层测试点（domain/data/UI） | P5-01～P5-09 真机 + 实际模型 + 保存数据 | 以需求文档用例为准 |
