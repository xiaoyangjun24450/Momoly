# 阶段 5 需求文档：地点拓展与整体验收

同阶段：[设计文档](设计文档.md) · [调研文档](调研文档.md)　｜　[文档总览](../README.md)　｜　前置 [阶段 4](../phase-04-proactive-messages/需求文档.md)

## 1. 阶段目标与可体验结果

让 agent 生成的新地点真正进入现有世界：用户可以像前往世界书已有地点一样选择出行方式、消耗游戏内时间前往，并在新场景中展开故事。随后在真实设备上完成五个阶段的完整回归与整体验收。

| 目标 | 说明 |
| --- | --- |
| 地点可生成 | agent 依据用户请求、当前世界设定、已有地点和出行信息生成新地点 |
| 地点可用 | 生成结果必须包含与已有地点的连接、可用出行方式和游戏内耗时，才构成可使用的新地点 |
| 出行可执行 | 新地点进入地点列表，可选择路线，按保存的耗时消耗游戏内时间后到达 |
| 故事可展开 | 角色按日程和位置自行移动后，在新地点参与线下故事并进入共同记忆 |
| 流程可回归 | 五阶段全部用例在真实设备、实际模型服务上贯通，并留下验收记录 |

完成后应能看到：地点拓展入口、新地点与场景描述、更新后的地点列表、可执行的出行方式和耗时、新场景故事，以及结束故事后带着记忆继续进行的自然聊天。

本阶段不新增独立于五阶段之外的能力：地点生成、出行接入、故事衔接均为既有模块的扩展；整体验收覆盖全部已确认需求，不把"文档写完"或"版本可安装"当作功能交付完成。

## 2. 范围

### 2.1 范围内

| 项 | 内容 |
| --- | --- |
| 地点拓展 agent（模块 10、11） | 接收用户请求，输出新地点名称、场景描述、与已有地点的连接、出行方式和游戏内耗时 |
| 新地点接入世界与出行（模块 2、4） | 按既定数据格式写入当前世界，沿用同名条目保留旧条目规则，新增路线可被原出行模块使用 |
| 新场景中的角色与故事（模块 5、6、7、8） | 复用既有约定、日程、出行、故事和记忆流程，在新地点完成见面与线下故事 |
| 完整用户流程回归（全部模块） | 贯通导入校验、世界合并、纯消息聊天、时间、出行、日程、多人故事、共享记忆、快穿冻结、主动通知和地点拓展 |
| 最终交付物 | 可安装版本、构建标识、验收记录、截图录屏、未解决问题清单 |

### 2.2 范围外

| 项 | 说明 |
| --- | --- |
| 独立的地点编辑库/编辑器 | 本阶段的新地点来源是 agent 生成；不新增"内置地点库 + 自定义地点编辑页"作为交付能力（历史方案见 [调研文档](调研文档.md) §4） |
| 新的邀约系统、场景引擎、故事格式 | 属阶段 3 交付；本阶段只验证新地点沿用既有流程 |
| 备份恢复、旧版本迁移与升级验收 | 已确认取消独立模块；只做正常页面切换与重开 APP 的业务连续性检查 |
| 生成内容的固定措辞、固定地点、固定分钟数 | 验收检查是否符合世界设定、是否真实保存并可执行，不强制模型输出指定文本或数值 |
| 多世界同时运行、服务端托管 | 已确认需求为同一时间只有用户所在的世界运行；本阶段不新增服务端能力 |

## 3. 功能需求

### 3.1 地点拓展 agent（模块 10、11）

| 项 | 要求 |
| --- | --- |
| 输入 | 用户的地点拓展请求、当前世界设定、已有地点和出行信息 |
| 输出 | 新地点名称与场景描述、与已有地点的连接、可用出行方式和相应游戏内耗时 |
| 功能 | 生成符合当前世界设定的地点；使用后续调研确定、并已在阶段 2 接入的表达方式；给出连接已有地点的出行信息、方式和耗时。具体字段结构见 [阶段 1 调研文档](../phase-01-contacts-and-chat/调研文档.md) 的「待调研问题」，尚未定稿 |
| 硬性要求 | 仅有一段场景描写而没有出行信息，不构成可使用的新地点 |
| 示例 | 用户请求"在校园里增加一家靠近图书馆的咖啡馆"，agent 生成咖啡馆场景，并给出从图书馆前往的出行方式和耗时。验收使用实际生成并保存的数据，不强制模型输出某个固定分钟数 |

### 3.2 新地点接入世界与出行（模块 2、4）

| 项 | 要求 |
| --- | --- |
| 输入 | agent 生成的地点与移动信息、当前世界已有条目和地点数据 |
| 输出 | 合并后的世界书和地点列表、可执行的路线、新地点的持久化记录 |
| 功能 | 生成结果符合既定数据格式后写入当前世界；沿用同名条目保留旧条目的规则；新增路线可被原出行模块使用；不改变其他世界 |
| 冲突处理 | 地点名称冲突时不能悄悄覆盖旧内容；结果应能说明哪些内容实际被添加 |
| 示例 | 咖啡馆写入校园世界后在地点列表中可见；用户选择"从图书馆步行前往"，界面显示保存的耗时，进入路上状态，并在足够的游戏时间后到达 |

### 3.3 新场景中的角色与故事（模块 5、6、7、8）

| 项 | 要求 |
| --- | --- |
| 输入 | 新增地点、角色日程与约定、用户和角色的实际出行结果、共享记忆 |
| 输出 | 符合位置和日程的见面结果、新地点的线下故事、后续聊天可使用的共同经历 |
| 功能 | 新地点使用既有的约定、日程、出行和故事流程；角色也需要有合理的位置变化，不能因为地点生成完成就自动出现在那里；故事结束后的记忆进入原聊天 |
| 示例 | 用户约林夏空闲时去新咖啡馆，双方完成相应移动后进入故事；在咖啡馆聊到上次借的书，角色能够衔接旧记忆，并在之后聊天中记得这次见面 |

### 3.4 完整用户流程回归（全部模块）

| 项 | 要求 |
| --- | --- |
| 输入 | 统一角色卡、完整功能版本、实际模型服务和目标设备 |
| 输出 | 覆盖全部需求的验收记录、可安装交付版本、实际存在的功能限制或未通过项 |
| 功能 | 贯通导入校验、世界合并、有角色口吻的纯消息聊天、时间、出行、日程、多人故事、共享记忆、快穿冻结、主动通知和地点拓展；检查状态一致，线上不会残留线下叙事 |
| 示例 | 添加林夏后聊天约图书馆见面，途中继续聊天，与林夏和沈言经历借书故事；结束后快穿并返回，随后收到林夏主动消息；再生成咖啡馆并完成第二次见面，回到聊天时仍只显示自然的消息正文 |

## 4. 跨模块约束

| 编号 | 约束 | 适用模块 | 验收检查 |
| --- | --- | --- | --- |
| C1 | 生成结果必须带出行信息（连接已有地点、方式、游戏内耗时）才算可用地点，否则不构成可使用的新地点、不可前往 | 10、11、4 | P5-01、P5-02 |
| C2 | 合并沿用同名条目保留旧条目的既有规则；新生成内容不覆盖旧条目 | 2、10 | P5-03 |
| C3 | 冲突不能悄悄发生：结果需能说明哪些内容实际被添加、哪些因同名被保留 | 2、10 | P5-03 |
| C4 | 不能瞬移：用户与角色都按出行方式和耗时移动，未消耗足够时间不能到达；角色不会因地点生成完成就出现在新地点 | 4、5 | P5-04、P5-05 |
| C5 | 地点与路线只写入发起请求时所在的当前世界，其他世界不被加入该地点、不被修改 | 2、3 | P5-02、P5-06 |
| C6 | 线上只发布纯消息正文；动作、场景、旁白只出现在线下故事，主动消息与通知预览同样不出现叙事残留 | 6、7、9、12 | P5-08 |
| C7 | 正常页面切换或重新进入 APP 后，地点、消息、共同记忆和会话保持连续；这是业务连续性检查，不涉及备份恢复或迁移 | 2、4、6、8 | P5-07 |
| C8 | 同一角色始终只有一个持续会话；世界冻结期间不推进时间、不主动联系；线下故事期间禁止快穿 | 3、6、8 | P5-06、P5-09 |
| C9 | 验收以实际生成并保存的数据为准，不要求固定地点名或固定耗时；未通过的必要用例保持"未通过" | 全部 | 全部 |

## 5. 验收用例

准备：在已完成前四阶段的校园世界操作，使用符合届时已确定导入规则的角色卡和可用的实际模型服务；返程用例需在验收素材中同时提供返程路线。

| 编号 | 操作步骤 | 应看到的结果与通过标准 |
| --- | --- | --- |
| P5-01 | 请求在校园世界扩展一家咖啡馆。 | 得到地点与场景描述、连接已有地点的出行方式及耗时；结果符合当前世界设定。 |
| P5-02 | 查看世界书和地点列表。 | 新地点及出行信息已保存并可见，已有地点未被无关修改，其他世界没有被加入该地点。 |
| P5-03 | 让扩展请求涉及已有同名条目，检查合并结果。 | 原条目完整保留；不存在以新生成内容覆盖旧条目的情况；结果能清楚说明哪些内容实际被添加。 |
| P5-04 | 选择新地点和一种出行方式，分次推进游戏时间。 | 使用保存的实际耗时；未消耗足够时间时仍在路上；到达后位置正确，途中能聊天。 |
| P5-05 | 与空闲角色约在新地点见面，完成双方移动后开始故事。 | 角色没有瞬移；故事使用新场景，并能引用已有共同记忆。 |
| P5-06 | 结束新地点故事后聊天，再切换世界并返回。 | 新地点经历能进入原聊天；其他世界冻结规则正常；新地点和记忆保留。 |
| P5-07 | 离开新地点，正常切换页面或重新进入 APP，再查看地点和角色聊天。 | 新地点、已有消息和共同记忆仍可使用，角色会话不重复；这是正常业务连续性检查，不涉及备份恢复或迁移。 |
| P5-08 | 从包含动作和场景描写的新地点故事返回聊天，再触发一条主动消息。 | 普通回复和主动消息都恢复角色口吻与纯消息形式，不出现残留旁白、动作或内心独白；通知预览也一致。 |
| P5-09 | 在真实设备连续执行完整用户流程，并复测关闭 APP 后的通知。 | 各模块衔接正常；冻结、见面、记忆和通知没有互相矛盾；不以单独页面可用代替流程通过。 |

记录格式沿用 [文档总览](../README.md) §4：用例编号、构建与设备、实际操作结果、截图或录屏、结论、未解决问题。预期结果不能直接当作已通过。

## 6. 最终验收交付物

| 交付物 | 内容 |
| --- | --- |
| 可安装版本 | 安装包、构建标识及本次实际验证的设备和运行场景 |
| 证据材料 | 地点生成、路线和耗时、新地点故事的截图和录屏 |
| 验证记录 | 角色卡完整性、生成地点的路线数据、线上纯消息与线下故事边界的验证记录 |
| 回归汇总 | 五阶段全部用例的实际结果、完整用户流程录屏、尚未解决的问题清单 |

通过条件：新增地点可实际使用，全部已确认功能在完整流程中协同工作，线上保持自然的纯消息聊天。任何阶段尚未通过的必要用例都应继续标为未通过，不能仅以五份文档完成或版本可安装作为功能交付完成。

## 7. 依赖与待确认问题

### 7.1 依赖

| 依赖 | 说明 | 未满足时的处理 |
| --- | --- | --- |
| 阶段 1-4 验收通过 | 本阶段回归以既有能力为前置 | 未通过项继续记录，不用阶段 5 用例替代 |
| 阶段 2 出行数据表达 | 生成结果中的方式、耗时和路线必须与阶段 2 已接入的表达方式一致 | 表达方式未定前不锁定生成字段 |
| 阶段 2 角色日程与位置 | 角色需按日程移动后参与新地点故事 | 不许用瞬移或强制在场绕过 |
| 阶段 3 故事与记忆 | 新地点故事沿用既有故事流程和记忆回写 | 不另建故事格式或第二套记忆 |
| 阶段 4 通知 | 回归中检查主动消息与通知预览的纯消息形式 | 通知场景按目标设备实际结果记录 |
| 实际模型服务与目标设备 | 生成与故事内容需真实模型；通知和后台需真机 | 无实际模型或设备时不标记通过 |

### 7.2 待确认问题

| 问题 | 影响 | 当前处理 |
| --- | --- | --- |
| 地点/场景生成的结构化格式、必填字段与校验规则 | 决定"可用地点"的判定和合并行为 | 待调研，见 [调研文档](调研文档.md) §6；不预设字段 |
| 生成内容写入世界书的具体位置与表达 | 决定同名条目判断、导出兼容和阶段 2 读取方式 | 待调研；只确认"写入当前世界、同名保留旧条目" |
| 同名判定粒度（地点名/条目名/别名） | 影响 P5-03 的合并结果解释 | 待定，需在验收前明确 |
| 出行方式枚举与耗时单位 | 影响生成结果能否被原出行模块直接使用 | 以阶段 2 接入结果为准 |
| 路线是否双向、返程如何提供 | 影响"前往新地点后能否回家"及后续故事 | 待验收素材明确 |
| 生成失败或信息不全时的用户反馈 | 影响可用性与是否允许重试 | 待设计文档给出方案 |
| 发布版本标识与验收记录归档方式 | 影响最终交付物的一致性 | 沿用 [文档总览](../README.md) §4 记录格式与项目发布约定 |
