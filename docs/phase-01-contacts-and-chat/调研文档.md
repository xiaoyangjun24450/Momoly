## 1. 结论摘要

- **没有可直接移植的完整成品。** 旧调研扫描 GitHub 未找到同时具备「微信式 IM + SillyTavern 角色卡 + 本地主动消息 + 邀约式出门」的项目；最接近的 Muse 三件齐、缺出门。阶段 1 因此以复用 Momoly 自身的导入、世界书与生成链路为主，外部只借规则与设计。
- **角色卡导入：保留现有 Kotlin 链路，参考 SillyTavern 的兼容行为与 AIRI 的 V3 校验。** "酒馆能导入"不能作为本产品准入通过的证据：ST 的 V2/V3 校验都允许世界书缺失。
- **世界归类与「同名条目保留旧版」是自研业务规则。** 上游不统一（ST 提示覆盖同名书，本仓库旧行为生成独立副本），不能原样采用。
- **活人感与纯消息的交付形式已收窄**：当前可用的酒馆格式预设，或所有角色共用的常驻规则世界书；不把插件、脚本、EJS 模板或独立检查模型作为本阶段前提。
- **导入校验当前只确认一条**：角色卡未附带可读取的世界书则拒绝；书名为空沿用补名行为，不作为拒绝条件。最低内容清单、必填字段、关联校验均待调研（见第 6 节）。
- **默认资源**：内置一份预设 + 一份全角色常驻规则书，随包更新、固定 ID；只承载提示约束，不能保证模型每次合规。
- **许可**：生态以 AGPL/GPL 为主；非商业、无 LICENSE、All rights reserved 项目只借设计不搬代码，第三方素材不进仓库。

## 3. 关键机制与证据

### 3.1 角色卡与世界书格式

- **承载形式**：纯 JSON；PNG `tEXt`/`zTXt` 块（关键字 `chara` 对应 V1/V2、`ccv3` 对应 V3，值为 base64 JSON，可再 zlib 压缩）；V3 起另有 CHARX（zip 内 `card.json` + `assets/`），本仓库尚未覆盖（待核实）。
- **规范事实**：CCv2 中 `character_book`、书 `name`、条目 `name`/`comment` 均可缺省；角色文本字段有类型要求，但"字段存在"不等于"内容非空"。CCv3 增加资源、昵称、条目 ID 与匹配语义，但没有定义世界冻结、路线耗时或角色日程协议——阶段 2 的运行信息不能要求社区卡自带自造结构。
- **参考实现的差别**：SillyTavern 的 [PNG 解析器](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/src/character-card-parser.js) 同样优先 `ccv3`，但 [TavernCardValidator](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/src/validator/TavernCardValidator.js) 主要检查字段存在与部分容器类型，世界书可以缺失；AIRI 的 [CCv3 codec](https://github.com/moeru-ai/airi/blob/9e7917d9c660f4e8e05d3c04a5f71fe316c39b49/packages/ccc/src/codec/characterCardV3.ts) 用 Valibot 逐层校验并保留未知键，适合参考结构与错误路径；RisuAI 的 [角色卡导入与世界书转换](https://github.com/kwaroran/Risuai/blob/ea61945f9038e0189807d075f55f4e66ab7e98bf/src/ts/characterCards.ts) 依赖其数据库/资产/脚本，不能整段搬进 Kotlin。
- **兼容铁律**：`extensions` 未知键原样保留，新版本字段"读不懂也要能保存"；"能解析"不等于"已校验"。兼容范围应写成"PNG 容器 + V2/V3 基础字段及已支持的世界书语义"，而不是笼统的"完整支持 V3"。

### 3.2 世界归类与世界书合并

- **世界身份取书内 `name`**，不使用经文件名清理或自动加后缀的名称；建议只去首尾空白后精确比较，是否忽略大小写待定，不做模糊匹配合并不同世界。
- **同名条目保留旧完整条目**，不仅保留 `content`，还包括启用状态、关键词、插入位置、优先级、扩展与未知字段；合并以原始条目对象为依据，避免经精简模型重建导致信息丢失。
- **条目名映射候选**：非空 `name` 优先、非空 `comment` 回退（与 Risu 思路接近）；无名条目不能都当同名处理，不能直接按空字符串相等去重，也不把第一个关键词猜成标题。
- **名称与 ID 不是一回事**：不同书都常见 `id=0`，不能当作同一条目；转换前识别重复 ID，追加时分配不冲突的内部标识并保留来源 ID；无依据不改写扩展中引用的旧 ID。
- **共享世界书只保留一个有效版本**：导入第二张卡后两个角色都关联合并书，聊天不能同时注入卡内旧副本与合并书；世界书正文可能含私人关系与背景，合并存储不等于"全角色公共知识"授权。
- **失败不留半次合并**：先计算校验与合并结果，再整体提交联系人、世界关联与书内容；修改已有书也要能在提交失败时恢复。
- **上游对照**：ST 的 `importEmbeddedWorldInfo` 会提示覆盖同名书，本仓库旧行为生成独立副本并允许自动补书名（"角色名 世界书"），两者都不能原样满足当前规则。

### 3.3 活人感与纯消息输出

- **交付形式**：独立聊天预设（规则、顺序、覆盖行为集中管理）或共用常驻规则世界书（保留模型参数、可独立修改、一份复用于多角色），按需二选一，不堆叠重复规则；共用书不参与角色所属世界的归类。
- **"常驻"不等于必然全量进入每次请求**：不依赖关键词，但仍受概率、分组与 token 预算筛选；要在真实请求里确认规则存在，不能只看世界书开关。
- **提示约束不等于程序校验**：角色卡直接展示的开场白与备选、流式文本、正则与渲染转换，以及卡内 `system_prompt`/示例/深度提示都可能绕过或冲突；不能把"导入预设成功"当成纯消息验收通过。
- **参考**：MaiBot 把身份、行为风格、回复风格分开组织，中文口语与减少机械追问可借鉴；但其内置人设带固定身份与群聊语气、部分要求刻意残缺表达，不能套给所有角色，其"重试耗尽后沿用最后一次回复"也不符合"仍不合格则不发布"。AIRI 的 [message-split 提示](https://github.com/moeru-ai/airi/blob/9e7917d9c660f4e8e05d3c04a5f71fe316c39b49/integrations/telegram-bot/src/prompts/message-split-v1.velin.md) 按完整意思组织、只在自然停顿时拆分；AstrBot 的结果加工按分隔符/正则分段，适合 IM 发送但不等同语义节奏。
- **梦鲸思客 V5**：用户提供的 `梦鲸思客V5-1030-exp.json`（SHA-256 `96065d1e…68b635`）含 122 个提示条目、主顺序组启用 44 项、28 条正则、6 个脚本，当前配置为第三人称、转述抢话、动态长篇约 1000～2000 字、写作模式，是长篇共创预设而非即用纯消息私聊；本产品只提炼信息差、禁霸总、杀解释欲、结尾控制、不抢话方向，保留其"梦境思客Gemini"经典段落（用户指定），不采用 XML 正文协议、分析栏目、成人强化、脚本与压缩宏，也不直接套用其 200 万上下文与 3 万回复上限。
- **语义检查的可选方案**：提示词 + 标点/正则过滤只能减少明显标记；结构化 `messages` 输出便于协议层提取，但合法字符串仍可能是动作描写；候选全文检查 + 必要时改写/重生成 + 再检查最接近需求，但增加调用、等待与费用，检查模型也会误判——模型与重试预算待实测。

### 3.4 分段发送、插话与未发送草稿

- 阶段 1 已确认六条规则以产品需求第 2.6.1 节为准（归[需求文档](需求文档.md)），本节只记录调研依据：AIRI 的"完整意思优先、自然停顿才拆"与本需求方向一致；AstrBot 的按分隔符/正则分段可满足 IM 发送，但不足以证明语义节奏。
- 分段、发布前检查与旧队列取消属于 APP 流程，不引入外部机器人、语音服务或完整代理系统；角色卡/预设中的分段建议不能替代程序规则。

### 3.5 默认资源来源与边界

- 2026-11-04 证据：`data/resources/src/main/assets/defaults/online-chat-preset.json`（内容版本 4）与 `online-chat-worldbook.json`（版本 3）随 APP 内置，固定资源 ID；旧默认按内容版本替换（含旧版默认资源上的个人修改），用户自建或导入的独立资源不替换；共用书自动加入所有角色，不创建副本、不改变角色所属世界。
- 验证边界：资源模块 36 项测试与 Debug 构建通过，未安装手机、未调用真实模型、未执行原预设脚本——聊天质量与纯消息发布行为仍未验收；当前行为以[设计文档](设计文档.md)为准。
- 来源：产品要求 + 梦鲸思客 V5 + MaiBot/EchoText/RPG-Phone/Sudachi/AIRI 思路；参考附件不打包进 APP。

### 3.6 生态与竞品结论

- 需求已被市场验证（Muse、ZeroChat、小手机、柚月、Float 等），但"原生 Android + ST 卡 + 纯本地 + 邀约式出门"仍是空位；UI 外观不是护城河。旧调研的判断是"主动消息在开源里没有可直接搬的实现"，只有机制可借（EchoText 触发器、Veranima Gate、Miru AttentionEngine 等），投递仍需自建（阶段 4）。
- 常见形态是"手机壳 + 微信/QQ 式聊天 + 朋友圈/日记/小剧场"，多为 Web/PWA 或 Flutter/WebView，原生 Kotlin/Compose 少见；未读/置顶/免打扰等 IM 会话管理反而是竞品普遍没做全的点，但阶段 1 不据此扩大范围。
