# 阶段 2：世界时间、出行与角色日程

前置阶段：[阶段 1](phase-01-contacts-and-chat.md) 验收通过。  
状态：计划，尚未实现和验收。  
关联：[总计划与统一验收素材](README.md)、[产品需求](../roleplay-companion-requirements.md)。

## 1. 阶段目标和可视化结果

让世界和角色拥有可观察的时间、位置与活动。用户能够切换世界、选择推进的时长、选择出行方式，并在路上继续聊天。

完成后应能看到：世界选择页面、当前世界与游戏时间、其他世界的冻结状态、地点列表、出行方式和耗时、路上状态与剩余时间，以及角色当前地点和活动状态。

## 2. 功能模块

### 2.1 可运行的地点与出行设定（模块 2）

- 输入：已合并的世界书，包含地点、场景、路线、出行方式和耗时的信息。
- 输出：该世界的地点列表，以及可供出行模块读取的路线、方式和耗时数据。
- 具体功能：按后续调研确定的数据表达和读取方式，把世界书内容转换成程序可以使用的设定。已有移动耗时以世界书为来源；具体字段和是否需要扩展结构暂不预设，见 [待调研事项](character-card-import-spec.md)。
- 例子：世界书写明“家到教室步行 20 分钟、骑行 8 分钟”，地点页面选择教室后显示这两种方式和对应耗时。

### 2.2 世界运行、游戏时间与冻结（模块 3）

- 输入：目标世界、当前世界状态、各世界保存的游戏时间、自然推进或用户选择加速的时长。
- 输出：唯一运行的世界、更新后的游戏时间、其他世界的冻结状态、本次推进的时间区间。
- 具体功能：世界之间直接切换；切换时冻结原世界并恢复目标世界；时间加速只作用于当前世界；返回原世界时从冻结点继续。聊天发送和回复入口遵守世界状态。世界进度、用户行程和角色状态作为业务数据记录，正常重新进入时保持连续，不额外建设备份或迁移模块。
- 例子：校园世界从 08:00 推进到 08:30，奇幻世界仍停在 10:00。切换到奇幻世界后推进 10 分钟，再返回校园世界，校园世界仍从 08:30 继续。
- 实施约定：本阶段确定未手动加速时的游戏时间推进方式，以及跨过多个到期事件时的处理顺序。游戏时间和消息实际收发时间分别保存。

### 2.3 用户出行与途中聊天（模块 4、6）

- 输入：出发地点、目标地点、所选出行方式、世界书的移动信息、游戏时间推进量。
- 输出：出行计划、所需时间、预计到达时间、剩余时间、“路上”状态和到达后的新位置。
- 具体功能：出发后进入路上状态，消耗足够的游戏内时间后才能到达；允许选择推进的时长；途中保留聊天入口。角色是否回复仍由世界和角色状态决定。
- 例子：08:00 从家步行去教室，预计 08:20 到达。推进 10 分钟后仍在路上，剩余 10 分钟；这时可以给沈言发消息，再推进 10 分钟后显示已到教室。

### 2.4 角色日程、位置和回复时机（模块 5、6）

- 输入：角色设定、已有日程、世界时间、地点与路线、已接受的约定、当前活动。
- 输出：角色的位置、活动和移动进度；能否见面、能否回复；后续日程变化和待回复消息的处理机会。
- 具体功能：角色依照日程移动；移动也遵守地点之间的耗时；忙碌时可以暂缓回复，空闲后处理待回复消息；世界冻结时日程、移动和回复全部暂停。日程信息作为后续赴约和主动联系的基础。
- 例子：林夏 08:00—08:30 在教室忙碌，08:30 出发去图书馆，08:40 到达。用户在 08:10 发消息，界面能显示角色忙碌；到达空闲时段后角色可以回复。
- 实施约定：初始地点与日程依据的来源和格式待调研；本阶段根据明确后的方案形成实际日程，处理空档、出行和已接受约定。验收使用总计划给出的可重复场景，不预先要求角色卡包含指定作息字段。

### 2.5 后台通知的最小验证（模块 12，正式功能在阶段 4）

- 输入：一个确定会到期的测试任务、目标设备和拟采用的后台运行方式。
- 输出：真实系统通知及各运行场景的验证记录。
- 具体功能：提前验证后台执行与通知路径，不接入完整的角色主动联系策略。分别记录退到后台、锁屏、划掉任务列表等场景；系统强制停止作为独立场景记录，不能与普通关闭混为一谈。
- 例子：在验收环境设置一条确定到期的测试消息，关闭界面后在通知栏收到它，并记录实际到达时间和设备条件。这只证明技术路径，不代表角色主动联系已经完成。

## 3. 阶段内执行顺序

1. 确定游戏时间、日程和后台运行的实现约定，进行最小后台通知验证。
2. 接入世界书中的地点、路线、出行方式和耗时。
3. 完成世界切换、时间推进、冻结和恢复。
4. 完成用户移动，再接入角色日程、角色移动和忙闲回复。
5. 完成状态展示、世界进度连续性和整体联调。

线下故事期间的快穿限制在阶段 3 接入故事状态；本阶段先提供世界切换和统一时间能力。

## 4. 完成后如何验收

准备：使用总计划中的时间、路线和日程。精确检查游戏时间时记录验收所用的自然推进规则，并在可重复的起始状态开始。

| 编号 | 操作步骤 | 应看到的结果与通过标准 |
| --- | --- | --- |
| P2-01 | 进入校园世界，查看地点和出行方式。 | 家、教室、图书馆可见；对应方式和耗时与世界书一致。 |
| P2-02 | 在校园世界推进 30 游戏分钟，查看两个世界的时间。 | 校园世界推进到对应时间；奇幻世界仍停在原时间并显示冻结。 |
| P2-03 | 切换到奇幻世界并推进时间，再返回校园世界。 | 切换无需出行等待；校园世界从冻结点继续，角色状态也从保存的位置继续。 |
| P2-04 | 在家选择步行去教室，先推进 10 分钟，再推进剩余时间。 | 途中显示路上和剩余时间；累计消耗 20 游戏分钟后到达，不能提前变成在教室。 |
| P2-05 | 从相同起点选择骑行路线。 | 显示并使用世界书给出的 8 分钟耗时；不同方式实际影响出行时间。 |
| P2-06 | 用户在路上时与空闲的沈言聊天。 | 可以收发消息，出行状态保持正确，不因聊天直接到达或重新计时。 |
| P2-07 | 分别推进到林夏的忙碌、移动和空闲时段。 | 界面依次显示教室忙碌、前往图书馆、在图书馆空闲；位置变化符合路线耗时。 |
| P2-08 | 忙碌时给林夏发消息，再推进到可回复时段。 | 用户消息保存；角色不会绕过忙闲规则即时回复；空闲后能处理待回复消息，且不重复发送。 |
| P2-09 | 让角色开始生成回复，随后切换世界。 | 原世界冻结后，未完成生成不能继续作为该世界的新消息提交或通知；返回后按保存状态和调度规则继续。 |
| P2-10 | 用户移动中切换世界，在另一个世界推进时间，再返回。 | 原世界的用户行程和角色日程未偷跑，从冻结进度继续。 |
| P2-11 | 保存移动状态，关闭并重新打开 APP。 | 当前世界、位置、移动进度和角色状态按已确定的时间规则恢复；冻结世界不推进。 |
| P2-12 | 在目标设备执行最小后台通知验证。 | 能展示真实系统通知；各运行场景分别留有实际结果；明确阶段 4 可采用的运行路径及待解决差异。 |

## 5. 验收交付物

- 世界选择、游戏时间、冻结状态、出行方式、路上状态和角色活动的截图。
- “推进时间—角色移动—切换世界—返回恢复”的连续录屏。
- 原始世界书与界面耗时的对照、时间和日程实现约定、后台通知验证记录。
- P2-01 至 P2-12 的实际结果，以及阶段 1 关键路径回归结果。

通过条件：当前世界的时间、用户出行和角色活动一致，其他世界全部冻结；后台通知具有已验证的实现路径。此时可以开始阶段 3。
