# 阶段 1：通讯录与聊天基础

前置阶段：无。  
状态：计划，尚未实现和验收。  
关联：[总计划与统一验收素材](README.md)、[产品需求](../roleplay-companion-requirements.md)。

## 1. 阶段目标和可视化结果

将当前 APP 的角色管理和聊天入口改造成“添加通讯录—按世界找联系人—进入唯一聊天”的体验。

完成后应能看到：添加联系人入口、具体到字段和条目的导入校验结果、按世界分组的通讯录、会话列表、微信式聊天气泡，以及可以查看的合并后世界书。聊天连接真实模型，角色回复有符合其性格的口吻，线上气泡只展示发给用户的消息。

## 2. 功能模块

### 2.1 角色卡导入与校验（模块 1）

- 输入：用户选择的 PNG 文件。
- 输出：角色信息、头像、附带世界书；导入成功后的联系人；或者明确的校验失败原因。
- 具体功能：复用 PNG 内角色信息提取能力；检查能够读取角色数据，且附带世界书存在、名称不为空；通过后进入世界归类和联系人添加。其余内容完整性和字段校验先列入 [格式校验待调研事项](character-card-import-spec.md)。“加好友”只表示把角色卡添加到通讯录。
- 例子：导入可读取且附带有名称世界书的“林夏.png”，进入后续添加流程；世界书缺失或名称为空时，指出具体问题，且不产生联系人或部分合并的世界。

角色卡和世界书的最低内容清单、必填字段、数据结构及关联校验方式先不写死，待后续调研再补充。除上述已明确规则外，不把此前草拟的字段、地点数量、作息或路线结构当作导入拒绝条件。

数据格式校验与聊天质量分别验收，不能以格式通过代替活人感和纯消息输出检查。

### 2.2 世界归类与世界书合并（模块 2）

- 输入：导入世界书的名称和条目、已存在的世界及其世界书。
- 输出：角色所属世界 ID、合并后的世界书、可供通讯录显示的世界分组。
- 具体功能：同名世界书加入同一个世界；名称尚不存在则创建对应世界；合并时追加不同名条目，同名条目保留原有完整条目。一个角色只关联一个世界。
- 例子：林夏与沈言的世界书都叫“校园世界”，两人进入同一分组。第二份书新增“教室”，但把“图书馆”关门时间改为 20:00；合并后追加教室，图书馆仍保留旧条目的 18:00。
- 实施说明：当前项目导入同名世界书会生成独立副本，本阶段要调整为上述行为。保留旧条目后的具体关联校验与运行数据读取方式待调研；实际移动在阶段 2 接入。

### 2.3 通讯录与角色唯一会话（模块 6）

- 输入：联系人、世界归属、现有会话、点击联系人或会话的操作。
- 输出：按世界分组的通讯录、会话列表、当前角色唯一的会话 ID 和历史消息。
- 具体功能：联系人展示名称和头像；会话列表展示角色与消息预览；同一联系人每次打开都复用同一会话；新的角色在需要建立会话时只创建一个会话。已有“新建话题”等入口需要与唯一会话规则保持一致。
- 例子：与林夏聊三次，退出聊天页面、切换到沈言，再返回林夏，仍看到同一段历史，不出现三个林夏会话。

### 2.4 微信式聊天与模型调用（模块 6、11）

- 输入：用户消息、当前角色卡、关联世界书、该角色的聊天历史和已配置模型服务。
- 输出：用户消息气泡、真实角色回复、发送或生成状态、更新后的消息预览。
- 具体功能：复用已有模型接口、提示词组装和消息存储；调整消息列表、角色头像、输入区和聊天导航，形成微信式使用方式。世界设定继续参与回复上下文，最终角色消息必须符合下一模块的线上输出规则。
- 例子：用户问林夏“图书馆几点关门”，传给模型的是合并后保留的旧设定。角色回复应与 18:00 的设定一致。

### 2.5 活人感预设与纯消息输出（模块 6、11）

- 输入：APP 的线上聊天预设、角色身份与性格、起始关系、世界设定、已有聊天上下文，以及当前输入。
- 输出：一条或少量符合该角色口吻的聊天消息；内容是角色真正发给用户的话，不夹带旁白、动作或内心独白。
- 具体功能：设置默认线上聊天预设，结合角色性格约束说话方式；区分聊天和故事的输出模式；检查生成结果是否符合纯消息要求。开场白、备选开场白、普通回复、重新生成及后续主动消息都使用相同规则。
- 例子：用户说“今天有点累”，林夏可以回复“今天怎么啦，事情很多吗？”；寡言的沈言可以回复“先歇会儿。要聊聊吗？”；不能回复“她心疼地望着你，伸手摸了摸你的头”。

活人感预设应覆盖：

1. 口吻和社交倾向来自角色卡，表达与双方当前关系一致；热情不等于一上来就亲密，寡言也不等于每次只说一个字。
2. 优先使用自然口语和合适长度的消息；根据内容需要分成少量消息，不机械地把每个句号拆成一个气泡。
3. 承接用户具体说过的话，回应问题、情绪和上下文；避免固定以“我理解你的感受”开头、每次都追问、重复复述或生成客服式长篇建议。
4. 允许符合角色的语气词、标点和适量表情，不用随机错别字、刻意装傻或固定撒娇制造活人感。
5. 线上只输出可发送的消息正文。禁止动作描写、场景描写、旁白、未说出口的内心独白、角色名冒号和小说式段落；有无括号或星号都一样。
6. APP 的线上纯消息要求不被角色卡的 system_prompt、聊天示例或关联预设覆盖；与要求冲突的叙事提示只在适合的线下故事模式使用。

| 情况 | 可以作为线上消息 | 不能作为线上消息 |
| --- | --- | --- |
| 关心用户 | “今天怎么啦？要不要说说。” | “她皱起眉，担忧地看着你。” |
| 表达情绪 | “听你这么说，我有点担心。” | “她心想，自己一定要照顾好你。” |
| 汇报已知活动 | “我在图书馆，刚找到座位。” | “我走到你身边坐下，把书递给你。” |
| 邀请见面 | “要不要去图书馆见？” | “你们一起走进图书馆，找了张桌子坐下。” |

角色用消息描述自己的已知状态属于普通聊天；叙述并执行用户眼前的线下动作属于故事。赴约按钮等是 APP 控件，不能把小说旁白包装成角色消息。线下故事仍按阶段 3 支持动作和场景描写。

不能只接入一个预设就认定完成：需要检查实际回复。候选内容不符合线上格式时应改写或重新生成；仍不符合则不发布该条，提供重试反馈。验证完成前可显示“输入中”，不把待检查的旁白通过流式文本先展示给用户。不能仅删除括号或星号，留下仍在描写动作的正文。

## 3. 阶段内执行顺序

1. 准备现有格式的角色卡，以及无法读取、缺少世界书、世界书无名称的样例；其他内容完整性样例待调研后补充。
2. 完成已明确的导入校验、世界归类和世界书合并；具体字段与关联校验随调研结论补入。
3. 接入通讯录、唯一会话和会话列表。
4. 接入微信式界面、线上活人感预设、纯消息输出检查和现有模型链路。
5. 使用不同性格角色进行多轮对话与违规输出检查，再执行完整验收。

本阶段建立世界分组。世界时间、冻结、角色日程和线下故事在后续阶段交付。

本计划取消独立的保存、恢复与旧数据迁移功能模块，也不安排额外的备份或旧版本迁移验收。角色、消息和世界状态所需的正常记录随各业务功能处理。

## 4. 完成后如何验收

准备：使用总计划中的角色样例及已明确的无法读取、世界书缺失或无名称输入；配置可用模型服务。其他格式用例待调研后补充。聊天质量检查至少包含热情与寡言两种性格，每种进行不少于 10 轮连续对话，覆盖日常闲聊、具体问题、情绪表达和见面邀请。不得仅挑选最好的一条回复作为通过依据。

| 编号 | 操作步骤 | 应看到的结果与通过标准 |
| --- | --- | --- |
| P1-01 | 导入林夏 PNG，打开通讯录和聊天。 | 出现林夏姓名、头像和校园世界分组；联系人可以打开聊天。 |
| P1-02 | 再导入沈言、周宁和艾琳。 | 校园世界有三个联系人，奇幻世界有一个；同名世界没有被拆成带序号的副本。 |
| P1-03 | 按旧书、新书顺序导入；查看最终世界书。 | 教室条目已追加；图书馆条目只保留旧版本 18:00 的内容。 |
| P1-04 | 分别导入普通 PNG、世界书缺失、世界书名称为空的卡。 | 都提示对应问题；联系人和世界数量不变。 |
| P1-05 | 给林夏发消息；切换到沈言，再返回林夏，多次重复。 | 始终进入原会话，历史仍在，不出现同一联系人的多个会话。 |
| P1-06 | 询问图书馆关门时间，并继续问相关问题。 | 回答使用保留后的 18:00 设定，能承接上下文；气泡、输入区和预览正常。 |
| P1-07 | 分别与热情、寡言角色进行同类多轮聊天。 | 口吻体现角色差异；具体回应上下文，没有连续套用客服开头、重复复述、固定追问或无必要的长篇说教。 |
| P1-08 | 聊情绪、邀请见面，并要求角色描写拥抱、场景或内心活动。 | 线上仍只显示实际发给用户的话；括号内动作、无标记旁白、内心独白及小说段落都不能作为消息发布。 |
| P1-09 | 使用自带叙事开场白、动作示例或冲突 system_prompt 的角色卡，打开聊天并重新生成。 | 首次消息、备选开场白和重新生成都遵守线上模式；不能原样展示不合格叙事，冲突设定不能覆盖纯消息约束。 |
| P1-10 | 检查生成过程、检查不通过后的处理和最终消息。 | 生成中可显示输入中；未通过检查的旁白不会提前显示、进入历史或消息预览；失败可重试，不靠只删标点掩盖动作描写。 |
| P1-11 | 让角色自然汇报已知状态，例如“我在图书馆”。 | 正常的聊天自述可以通过，不把所有包含动作动词或情绪词的消息一律删除；也不会把叙述用户眼前行为的文本当作合格自述。 |

## 5. 验收交付物

- 可安装版本及构建标识。
- 通讯录分组、微信式聊天、校验失败提示、合并后世界书的截图。
- “导入—校验反馈—聊天—切换联系人”的录屏。
- 至少两种性格的连续聊天记录、最终使用的线上预设和纯消息检查结果。
- P1-01 至 P1-11 的实际结果记录；其他格式用例待调研后追加。

已明确部分的通过条件：导入与合并遵守已确认规则，聊天连接真实模型，角色表达自然且线上只发布消息正文。完整的格式校验范围和验收标准待后续调研补齐，不能把尚未确定的规则视为已实现或已验收。
