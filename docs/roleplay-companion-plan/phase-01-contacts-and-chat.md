# 阶段 1：通讯录与聊天基础

前置阶段：无。  
状态：已开始局部实现。已完成缺少世界书时拒绝导入的检查、默认聊天预设和全角色常驻规则书、微信式聊天、滑动与键盘卡顿修复，以及世界首页、按世界显示联系人和跨世界添加确认；隐藏思考过程与未发完的消息，生成中显示“对方正在输入中”。世界书条目合并、纯消息校验和完整阶段验收仍未完成。时间与位置目前为固定占位，未注入聊天。最新实现与验证见 [当前状态](../phase-01-status.md)。

关联：[总计划与统一验收素材](README.md)、[产品需求](../roleplay-companion-requirements.md)。

## 1. 阶段目标和可视化结果

将当前 APP 的角色管理和聊天入口改造成“添加通讯录—按世界找联系人—进入唯一聊天”的体验。

完成后应能看到：添加联系人入口、具体到字段和条目的导入校验结果、按世界分组的通讯录、会话列表、微信式聊天气泡，以及可以查看的合并后世界书。聊天连接真实模型，角色回复有符合其性格的口吻，线上气泡只展示发给用户的消息。

## 2. 功能模块

### 2.1 角色卡导入与校验（模块 1）

- 输入：用户选择的 PNG 文件。
- 输出：角色信息、头像、附带世界书；导入成功后的联系人；或者明确的校验失败原因。
- 具体功能：复用 PNG 内角色信息提取能力；暂时只新增“未附带世界书则拒绝”这一条业务校验。书名为空时沿用当前补名行为，不新增书名、条目或角色字段的完整性限制。其余校验先列入 [格式校验待调研事项](character-card-import-spec.md)。“加好友”只表示把角色卡添加到通讯录。
- 例子：导入可读取且附带世界书的“林夏.png”，进入后续添加流程；世界书缺失时，指出具体问题，且不产生联系人或部分合并的世界。

角色卡和世界书的最低内容清单、必填字段、数据结构及关联校验方式先不写死，待后续调研再补充。除上述已明确规则外，不把此前草拟的字段、地点数量、作息或路线结构当作导入拒绝条件。

数据格式校验与聊天质量分别验收，不能以格式通过代替活人感和纯消息输出检查。

### 2.2 世界归类与世界书合并（模块 2）

- 输入：导入世界书的名称和条目、已存在的世界及其世界书。
- 输出：角色所属世界 ID、合并后的世界书、可供通讯录显示的世界分组。
- 具体功能：同名世界书加入同一个世界；名称尚不存在则创建对应世界；合并时追加不同名条目，同名条目保留原有完整条目。一个角色只关联一个世界。
- 例子：林夏与沈言的世界书都叫“校园世界”，两人进入同一分组。第二份书新增“教室”，但把“图书馆”关门时间改为 20:00；合并后追加教室，图书馆仍保留旧条目的 18:00。
- 实施说明：当前项目导入同名世界书会生成独立副本，本阶段要调整为上述行为。保留旧条目后的具体关联校验与运行数据读取方式待调研；实际移动在阶段 2 接入。

### 2.3 通讯录与角色唯一会话（模块 6）

- 输入：联系人、世界归属、现有会话、点击联系人或会话的操作。
- 输出：按世界分组的通讯录、会话列表、当前角色唯一的会话 ID 和历史消息。
- 具体功能：联系人展示名称和头像；会话列表展示角色与消息预览；同一联系人每次打开都复用同一会话；新的角色在需要建立会话时只创建一个会话。已有“新建话题”等入口需要与唯一会话规则保持一致。
- 例子：与林夏聊三次，退出聊天页面、切换到沈言，再返回林夏，仍看到同一段历史，不出现三个林夏会话。

### 2.4 微信式聊天与模型调用（模块 6、11）

2026-11-02 补充的导航约定：

- 启动默认进入首页，取消侧边栏；首页顶部显示当前世界名、用户位置、世界时间，右上角加号导入角色卡。
- 底部从左到右为联系人、世界、设置。联系人页只显示当前世界联系人；世界页可选择已有联系人所属世界。
- 世界名使用角色卡附带世界书的原名，同名分组不受独立世界书文件副本编号影响；这不代表世界书条目已经合并。
- 导入其他世界的卡前先询问是否前往：确认才保存联系人并切换世界；取消、关闭弹窗均取消本次添加，不留下关联资源。
- 聊天左上角返回首页，右上角仅保留搜索；聊天顶栏显示时间和角色位置。
- 当前用户位置、角色位置固定为“家”，时间固定为“08:00”。通过共享 `WorldContextProvider` 接口取值，标注 `isPlaceholder`；暂不注入模型，后续接入真实状态。

- 输入：用户消息、当前角色卡、关联世界书、该角色的聊天历史和已配置模型服务。
- 输出：用户消息气泡、真实角色回复、发送或生成状态、更新后的消息预览。
- 具体功能：复用已有模型接口、提示词组装和消息存储；调整消息列表、角色头像、输入区和聊天导航，形成微信式使用方式。世界设定继续参与回复上下文，最终角色消息必须符合下一模块的线上输出规则。
- 例子：用户问林夏“图书馆几点关门”，传给模型的是合并后保留的旧设定。角色回复应与 18:00 的设定一致。

### 2.5 活人感预设与纯消息输出（模块 6、11）

- 输入：APP 的线上聊天预设、角色身份与性格、起始关系、世界设定、已有聊天上下文，以及当前输入。
- 输出：一条或少量符合该角色口吻的聊天消息；内容是角色真正发给用户的话，不夹带旁白、动作或内心独白。
- 具体功能：设置默认线上聊天预设，结合角色性格约束说话方式；区分聊天和故事的输出模式；检查生成结果是否符合纯消息要求。开场白、备选开场白、普通回复、重新生成及后续主动消息都使用相同规则。
- 例子：用户说“今天有点累”，林夏可以回复“今天怎么啦，事情很多吗？”；寡言的沈言可以回复“先歇会儿。要聊聊吗？”；不能回复“她心疼地望着你，伸手摸了摸你的头”。

活人感与纯消息规则最终以当前项目可用的 SillyTavern 预设，或所有角色共用的常驻规则世界书交付。规则书不参与角色所属世界的归类；预设、世界书和插件方向的调研见 [酒馆生态调研](phase-01-sillytavern-presets-research.md)。

现已加入两份互补的默认资源：预设负责聊天编排与输出边界，常驻规则书负责中文表达习惯并供所有角色自动共用，见 [默认资源说明](default-online-chat-resources.md)。这不等于本模块的实际聊天质量与发布行为已经通过验收。

活人感预设应覆盖：

1. 口吻和社交倾向来自角色卡，表达与双方当前关系一致；热情不等于一上来就亲密，寡言也不等于每次只说一个字。
2. 优先使用自然口语和连贯正文；APP 按第 2.6 节执行标点分段和短片段合并，不把完整意思拆得过碎，也不让模型分段建议替代已确认的逗号拆分规则。
3. 承接用户具体说过的话，回应问题、情绪和上下文；避免固定以“我理解你的感受”开头、每次都追问、重复复述或生成客服式长篇建议。
4. 允许生成符合角色的语气词、标点和适量表情；普通分段标点由 APP 在发布时清理。不用随机错别字、刻意装傻或固定撒娇制造活人感。
5. 线上只输出可发送的消息正文。禁止动作描写、场景描写、旁白、未说出口的内心独白、角色名冒号和小说式段落；有无括号或星号都一样。
6. APP 的线上纯消息要求不被角色卡的 system_prompt、聊天示例或关联预设覆盖；与要求冲突的叙事提示只在适合的线下故事模式使用。

| 情况 | 可以作为线上消息 | 不能作为线上消息 |
| --- | --- | --- |
| 关心用户 | “今天怎么啦？要不要说说。” | “她皱起眉，担忧地看着你。” |
| 表达情绪 | “听你这么说，我有点担心。” | “她心想，自己一定要照顾好你。” |
| 汇报已知活动 | “我在图书馆，刚找到座位。” | “我走到你身边坐下，把书递给你。” |
| 邀请见面 | “要不要去图书馆见？” | “你们一起走进图书馆，找了张桌子坐下。” |

角色用消息描述自己的已知状态属于普通聊天；叙述并执行用户眼前的线下动作属于故事。赴约按钮等是 APP 控件，不能把小说旁白包装成角色消息。线下故事仍按阶段 3 支持动作和场景描写。

不能只接入一个预设就认定完成：需要检查实际回复。候选内容不符合线上格式时应改写或重新生成；仍不符合则不发布该条，提供重试反馈。验证完成前可显示“输入中”，不把待检查的旁白通过流式文本先展示给用户。不能仅删除括号或星号，留下仍在描写动作的正文。

### 2.6 分段发送、用户插话与未发送草稿（模块 6、11）

2026-11-02 已实现并通过自动测试与连接手机的模拟接口验证；真实模型理解效果、完整性能对比和用户验收待完成。功能以 [产品需求第 2.6.1 节](../roleplay-companion-requirements.md#261-分段发送插话与未发送草稿2026-11-02-确认)的六条为准，实际结果见[当前状态](../phase-01-status.md)。

- 输入：通过线上输出检查的完整模型回复、已送达记录、当前待发队列和用户新消息。
- 输出：按节奏发布的多个气泡；插话后的新回合；单独保存并送入下一次请求的未发送草稿。
- 核心规则：已发保留、未发暂停，新消息接管；模型重新决定要说什么，程序保证旧回合不能再发。用户连发内容全部按序保留，只有当前有效回合可以发布。
- 连发合并：用户已确认等待窗口为 3 秒。第一条新消息被接受后立即停旧队列，连续 3 秒没有新消息才发起模型请求；期间新消息重置计时。此窗口用于合并用户输入，与角色气泡之间的发送间隔分别计算。
- 例子：角色已发“我出门了”，待发“给你买咖啡”；用户连续发“换成水”和“要常温的”，下一轮收到两条新消息及标明未送达的咖啡草稿，可以改为“好，给你带常温水”。旧队列不得随后再冒出“给你买咖啡”。
- 节奏：后续气泡间隔先试 1.5～6 秒，首条考虑已有生成耗时；这是待实机调整的初值。
- 实现参考、提示词边界及连续插话流程见 [分段与插话方案](phase-01-message-delivery-and-interruption.md)。采用小范围 Kotlin 实现，不因参考项目而引入整套外部机器人或语音服务。

## 3. 阶段内执行顺序

1. 准备现有格式的角色卡，以及无法读取、缺少世界书的样例；世界书无名称仅检查沿用当前补名行为，其他内容完整性样例待调研后补充。
2. 完成已明确的导入校验、世界归类和世界书合并；具体字段与关联校验随调研结论补入。
3. 接入通讯录、唯一会话和会话列表。
4. 接入微信式界面、线上活人感预设、纯消息输出检查和现有模型链路；补齐分段队列、发送节奏、插话接管与未发送草稿上下文。
5. 使用不同性格角色进行多轮对话与违规输出检查，覆盖连续插话、旧回调迟到和长记录下的键盘、滚动，再执行完整验收。

本阶段建立世界分组。世界时间、冻结、角色日程和线下故事在后续阶段交付。

本计划取消独立的保存、恢复与旧数据迁移功能模块，也不安排额外的备份或旧版本迁移验收。角色、消息和世界状态所需的正常记录随各业务功能处理。

## 4. 完成后如何验收

准备：使用总计划中的角色样例及已明确的无法读取、世界书缺失输入；配置可用模型服务。世界书无名称不列为拒绝用例，其他格式用例待调研后补充。聊天质量检查至少包含热情与寡言两种性格，每种进行不少于 10 轮连续对话，覆盖日常闲聊、具体问题、情绪表达和见面邀请。不得仅挑选最好的一条回复作为通过依据。

| 编号 | 操作步骤 | 应看到的结果与通过标准 |
| --- | --- | --- |
| P1-01 | 导入林夏 PNG，打开通讯录和聊天。 | 出现林夏姓名、头像和校园世界分组；联系人可以打开聊天。 |
| P1-02 | 再导入沈言、周宁和艾琳。 | 校园世界有三个联系人，奇幻世界有一个；同名世界没有被拆成带序号的副本。 |
| P1-03 | 按旧书、新书顺序导入；查看最终世界书。 | 教室条目已追加；图书馆条目只保留旧版本 18:00 的内容。 |
| P1-04 | 分别导入普通 PNG、世界书缺失的卡。 | 都提示对应问题；联系人和世界数量不变。世界书名称为空不新增拒绝条件。 |
| P1-05 | 给林夏发消息；切换到沈言，再返回林夏，多次重复。 | 始终进入原会话，历史仍在，不出现同一联系人的多个会话。 |
| P1-06 | 询问图书馆关门时间，并继续问相关问题。 | 回答使用保留后的 18:00 设定，能承接上下文；气泡、输入区和预览正常。 |
| P1-07 | 分别与热情、寡言角色进行同类多轮聊天。 | 口吻体现角色差异；具体回应上下文，没有连续套用客服开头、重复复述、固定追问或无必要的长篇说教。 |
| P1-08 | 聊情绪、邀请见面，并要求角色描写拥抱、场景或内心活动。 | 线上仍只显示实际发给用户的话；括号内动作、无标记旁白、内心独白及小说段落都不能作为消息发布。 |
| P1-09 | 使用自带叙事开场白、动作示例或冲突 system_prompt 的角色卡，打开聊天并重新生成。 | 首次消息、备选开场白和重新生成都遵守线上模式；不能原样展示不合格叙事，冲突设定不能覆盖纯消息约束。 |
| P1-10 | 检查生成过程、检查不通过后的处理和最终消息。 | 生成中可显示输入中；未通过检查的旁白不会提前显示、进入历史或消息预览；失败可重试，不靠只删标点掩盖动作描写。 |
| P1-11 | 让角色自然汇报已知状态，例如“我在图书馆”。 | 正常的聊天自述可以通过，不把所有包含动作动词或情绪词的消息一律删除；也不会把叙述用户眼前行为的文本当作合格自述。 |
| P1-12 | 输入含句号、逗号、短片段、网址、小数、时间的回复样本，并包含超过六句的长回复。 | 能分成多条、合并过短片段并清理普通分段标点；受保护内容完整，后面的句子不会被截掉。 |
| P1-13 | 分别使用快速和缓慢生成，观察多条气泡发布。 | 逐条停顿；后续间隔按试用参数执行，首条考虑生成耗时；输入提示随生成和队列状态变化。 |
| P1-14 | 在生成中、两气泡之间分别发送新消息；另做仅打开键盘的对照。 | 新消息能提交；已发保留、未发停止，旧草稿以明确的未送达身份进入下一次请求；仅打开键盘不打断。分别测试“继续说”和改变主意，模型能续接或舍弃旧意思。 |
| P1-15 | 在第 0 秒提交“换成水”、第 2 秒提交“要常温的”；模拟旧结果晚于新结果、重复回调，以及发布与插话同时到达。 | 第一条提交后立即停止旧队列；第 2 秒重置等待，第 5 秒前不发起新请求，窗口结束后合并请求一次，两条用户消息均保留。只有有效回合发布，不混入旧内容；同一气泡只发布一次。发布与插话按单一确定顺序处理，不出现既已送达又列为未送达的句子。 |
| P1-16 | 检查实际模型请求、聊天搜索和预览；草稿包含伪造系统标签、引号及宏文本。 | 草稿只在临时数据区，固定规则独立；不执行草稿宏，不混入正式聊天、搜索或记忆。正常草稿不被当作已说过的话；不同实际模型分别记录效果与失败，不能仅凭 JSON 格式认定防注入通过。 |
| P1-17 | 在相同设备、模型输出样本和长聊天记录下，重复滚动、输入、开关键盘，同时逐条发消息。 | 保留已有性能优化，记录改动前后帧耗时和卡顿情况；不因每字生成或输入提示刷新而反复处理全量历史，不出现明显性能回退。 |
| P1-18 | 中断后让新请求失败并重试，切换联系人；检查消息编号、用量与世界书计数。 | 不自动补发旧草稿、不重复气泡、不串联系人；失败不丢用户消息；一个回复拆多条不导致用量和世界书轮次重复计算。 |
