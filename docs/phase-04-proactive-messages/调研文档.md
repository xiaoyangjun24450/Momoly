## 1. 结论摘要

| 结论 | 依据 |
| --- | --- |
| 主动消息"触发 + 生成 + 投递"机制在开源项目中已较成熟，但"ST 角色卡 + 微信式 UI + Android 原生主动消息/通知"三件套齐全的项目没有；Muse 是最接近的同栈同形态项目（缺出门玩法） | 同类项目对标、notes/05、notes/06 |
| 触发机制可归为三类：规则/概率定时（ZeroChat、EchoText）、状态机驱动（jiwen、溪语 AI、KaijiBot）、生活日程驱动（溪语 AI、AI Pocket Chat）；当前需求要求"性格、日程、记忆、约定共同决定"，至少需要规则 + 日程/状态两类 | notes/06 §三、§四；调研报告 §3.3 |
| 冷却、概率、静默时段、等回复禁发、连续未回退避是行业常见防打扰手段；但当前产品明确"频率由角色性格决定、不提供免打扰"，因此这些只能作为内部实现约束，不能成为用户可见开关，旧设计的"免打扰四件套"中静默时段/免打扰被取代 | notes/06 §四、§五；design/03 §2.5；需求 §2.9 |
| 无服务端时 Android 后台投递只有本地调度路径：WorkManager（周期下限 15 分钟、受 Doze/ROM 延后）、精确闹钟（Android 14 默认拒绝）、前台服务（Android 14 类型与商店政策）各有硬限制；force-stop 后全部失效 | notes/02 §3.1、调研报告 §3.3、Android 官方文档 |
| 通知权限与渠道有平台硬约束：API 33+ 需运行时 `POST_NOTIFICATIONS`，渠道创建后 importance 不可程序修改，渠道被用户调低只能读取并提示 | notes/02 §3.3、Android 官方文档 |
| 许可混杂（MIT/GPL/AGPL/双许可/NC/无许可），所有项目只可借机制，代码与素材均不可搬；Momoly 自身为 AGPL-3.0 | 各项目 LICENSE；仓库 LICENSE 文件 |

## 3. 关键机制与证据

### 3.1 触发信号分类

| 类别 | 代表实现与证据 | 对阶段 4 的取舍 |
| --- | --- | --- |
| 时间类 | EchoText 14 类触发器含 Check-In/Morning Wave/Late Night；ZeroChat 随机间隔 + 定时任务；dylan-heartbeat 白天/夜间双阈值 | 当前需求要求"时间、日程"参与，但具体时段规则不写入产品要求，留给设计 |
| 状态类 | jiwen 五轴漂移与阈值；溪语 AI 10 维情绪；KaijiBot 画像/信任 | 当前需求有"角色状态/性格"，但未要求完整情绪系统；可用最小状态集 |
| 生活/日程类 | 溪语 AI 日程空隙与睡眠窗；AI Pocket Chat 日程/情绪/成长；OrangeChat 生活感知 | 当前需求明确"日程"，可直接复用阶段 2 的日程与忙闲；不做完整生活模拟 |
| 事件类 | 溪语 AI 开放环/纪念日；EchoText Memory Nudge / Affection Reciprocation | 当前需求有"约定、共同经历"，映射为动机来源，不写死话术 |
| 随机类 | ZeroChat 随机、dylan-heartbeat AI 自主沉默、jiwen 确定性漂移（反例） | 随机只能作为节奏手段，不能替代性格差异，否则无法验收 P4-02 |
| 用户活动类 | 溪语 AI"读空气"（连续 3 条未回闭嘴）、KaijiBot 不回复自然收敛、旧设计"用户活动重置" | 可作为内部约束（避免打扰/重复），但当前不做免打扰开关 |

### 3.2 节奏与约束机制证据

| 机制 | 证据 | 与当前需求的关系 |
| --- | --- | --- |
| 每日上限/频率档位 | KaijiBot 每日 1–2 条自持上限；旧 design/03 四档频率 + `dailyCap=3` | 当前需求改为"频率由性格决定"；上限若保留应作为内部约束，不是用户档位 |
| 冷却/最小间隔 | 旧设计好友日上限 → 全局上限 → 最小间隔；dylan-heartbeat 昼夜双间隔 | 可用于实现性格化节奏，需保证与"性格差异"一致且可解释 |
| 静默/免打扰时段 | 旧设计 23:00–08:00；ZeroChat 安静时间；XiYu 睡眠窗 | **当前明确不做免打扰**；旧方案被取代，不能作为验收项 |
| 等回复禁发 | 旧设计"最后一条是主动消息且用户未回则跳过" | 可用于避免自说自话，但不能形成用户可见"暂停"状态 |
| 连续无回应退避 | 溪语 AI 连续 3 条未回闭嘴；notes/06 建议 2 次退避 | 可作为内部策略；当前需求未规定，属待定 |
| 素材级防复读 | 溪语 AI 3-gram Jaccard + 14 天梗冷却；notes/06 建议本地字符串校验 | 当前需求要求"不重复"，可借思路；成本低、零 API |
| 可解释性 | jiwen `getTriggerTrace()`；XiYu emotion-debug | 验收需要记录"联系原因与计划时间"，内部记录即可，不展示给普通用户 |

### 3.3 Android 调度机制对比（无服务端）

| 方案 | 关键事实 | 结论/限制 |
| --- | --- | --- |
| WorkManager 周期任务 | 最小周期 15 分钟（AndroidX `MIN_PERIODIC_INTERVAL_MILLIS`），最小 flex 5 分钟；Doze/ROM 会延后；重启后自动恢复 | 可作为关闭 APP 后的候选执行路径；不承诺准点 |
| WorkManager 一次性 + 延时 | 可指定初始 delay，仍受 Doze 影响、不精确 | 可用于"下一次检查"排期，减少空转 |
| AlarmManager 精确闹钟 | `setExactAndAllowWhileIdle` 可到分钟；Android 12+ 需 `SCHEDULE_EXACT_ALARM`；Android 14 新装默认拒绝 | 不列为本阶段默认路径；若需要必须带权限检查与降级 |
| 前台服务 | Android 8+ 需常驻通知；Android 12+ 后台启动受限；Android 14 必须声明 `foregroundServiceType` | 默认不做常驻前台服务；短时生成是否使用需单独评估 |
| FCM/厂商推送 | 准点但需要服务端与各厂商接入 | 不适用（纯本地、无服务端） |
| 回前台补发 | 零新系统依赖、实现简单；但只在用户打开 APP 后生效 | **不能替代关闭期间的通知**（需求 P4-07 明确）；只能作为恢复与兜底 |

### 3.4 通知权限与渠道矩阵

| 能力 | 平台要求 | 阶段 4 含义 |
| --- | --- | --- |
| 通知渠道 | API 26+ 必须创建；渠道创建后应用不能修改 importance | minSdk 26；需预建渠道并读取用户调整后的真实 importance |
| 运行时通知权限 | API 33+ 需 `POST_NOTIFICATIONS`；被拒则无法发通知 | 目标设备需允许通知；被拒时生成与未读不阻断（产品行为待确认） |
| 精确闹钟权限 | API 31+ `SCHEDULE_EXACT_ALARM`；API 34 新装默认拒绝 | 不作为默认路径；需要时引导并降级 |
| 前台服务类型 | API 34 起必须声明类型；商店政策限制 | 默认不用常驻服务 |
| 电池优化白名单 | `isIgnoringBatteryOptimizations` 可检测，跳设置页引导 | 只引导，不静默申请豁免 |
| 厂商自启动/后台弹窗 | 各 ROM 设置页不同 | 需逐家验证，文案参考 dontkillmyapp，不承诺 100% 到达 |

### 3.5 通知点击直达会话

旧设计（design/02 §1.6）已给出形态：`MainActivity` 设 `singleTop`，通知 `PendingIntent` 携带 `charFile`（优先）或 `sessionId`，`onCreate`/`onNewIntent` 统一交给会话打开逻辑，避免被启动默认会话覆盖。当前工程尚未实现该入口（见[设计文档](设计文档.md)§5），阶段 4 需要补齐 Manifest、入参处理与"通知打开后清未读/取消通知"的联动。

## 4. 历史方案与差异

旧调研（2026-10-31，已归档到 `build/docs-before-cleanup/2026-11-04/momoly-research/`）中的 `design/03-主动消息.md` 是阶段 4 最重要的历史方案。其与当前需求一致的部分可直接作为实现参考，冲突部分以当前需求为准。

| 旧设计要点 | 旧方案内容 | 当前需求 | 结论 |
| --- | --- | --- | --- |
| 频率档位 | 4 档（Quiet/Relaxed/Natural/Lively），每档配置每日批次、最小间隔、真发概率 | 频率由角色卡中的角色性格决定，不采用所有角色统一的联系频率 | **被取代**；性格参数化可沿用"间隔+概率"实现，但不暴露用户档位 |
| 触发规则表 | 8 条内置规则：纪念日/节日/久别/冷场/修复/早晨/傍晚/周末随机 | 只要求结合性格、时间、日程、状态、记忆、约定；未固定规则清单 | 规则表降级为**实现参考**，不是产品承诺；不能反过来限制需求 |
| 防打扰四件套 | 频率上限+冷却、等回复禁发、用户活动重置、总开关+免打扰时段 | 明确不提供免打扰，聊天新消息始终通知 | 免打扰/静默/开关**被取代**；冷却、等回复、用户活动可作为内部约束 |
| 免打扰时段与安静渠道 | 23:00–08:00 不生成 + `proactive_messages_quiet` 低打扰渠道 | 不做免打扰；通知始终按聊天新消息处理 | **被取代**；只保留一个正常通知渠道 |
| 每好友/全局每日上限 | `dailyCap=3`、`minIntervalMinutes=90`、tier 概率 | 需求未规定配额与间隔数值 | **待定**；若保留需产品确认，不得作为验收标准 |
| WorkManager 15 分钟周期 | MVP 回前台补发，P1 引入 15 分钟 Worker | 后台路径以阶段 2 P2-12 验证为准 | **机制约束而非产品承诺**；15 分钟不能写进验收 |
| 回前台补发为主投递 | MVP=回前台补发+通知；App 前台时不发系统通知 | P4-07 明确不能以重新打开后补发代替关闭期间通知 | **降级为兜底**；关闭期间必须尝试真实后台通知 |
| 生成 1–3 条 `<msg>` 模板 | 单次生成 1–3 条、45s 超时、`maxTokens=320`、非流式 | 需求只要求"与联系原因相关的角色消息" | **实现细节待定**；条数/超时/预算未被产品确认 |
| 幂等与单事务 | `batchId` 幂等 + `commitProactiveBatch` 单事务 | 要求不重复生成/写入/通知 | **一致**，可沿用思路（键名与表结构按当前工程重定） |
| 通知预览开关与双渠道 | `notificationPreview` 可关预览；两渠道 | 通知预览为消息正文，不出现动作/旁白；不提供免打扰 | 预览开关**不在当前需求**；预览内容要求保留 |
| 生活感 `life`/情绪 | P2 情绪能量与好感，进 Prompt | 需求含"角色状态"，未要求完整生活模拟 | 可作内部状态来源，范围待定 |
| 数据键假设 | `FriendStore`、好友体系、未读字段等 | 当前工程是角色卡 + 会话（`charFile`/`sessionId`），无好友 Store | **需按当前工程重建**，旧字段不能照搬 |
| 1 好友 1 会话 | 已锁定 | 一致 | **沿用** |
