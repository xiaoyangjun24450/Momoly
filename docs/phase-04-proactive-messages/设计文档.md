## 1. 目标与约束

本设计回答阶段 4"怎么做"：主动联系如何判定与生成、后台如何调度与校验、通知如何送达并跳回原会话、任务与去重如何持久化。当前处于**计划态**，尚未落码；现状核实见 §5。

| 约束 | 内容 | 依据/影响 |
| --- | --- | --- |
| 纯本地、无服务端 | 不能使用 FCM/厂商推送，后台唤醒只能依赖设备本地调度 | 项目定位与工程现状 |
| 复用现有生成链路 | 主动消息复用阶段 1 的 Prompt 编译、世界书激活、预设、生成执行与纯消息规则，不另建第二套模型调用 | 需求 §3.2；`:domain:generation` 已有能力 |
| 阶段 2 能力与结论输入 | 到期判定、冻结/恢复、角色忙闲读阶段 2 领域能力；后台路径以 P2-12 实测为准，不重新论证可行性 | 需求 §3.3、§7 |
| 一个角色一个世界一个会话 | 主动消息写入该角色唯一会话，不新建会话、不伪造用户发言 | 需求 §3.2；阶段 1 规则 |
| 不做免打扰 | 不设静默时段、会话免打扰、通知开关替代品；聊天新消息始终通知 | 需求 §3.4、决策记录 |
| 通知只针对已提交消息 | 通知在落库事务成功之后构建，失败不通知、不指草稿 | 需求 §3.4、P4-09 |
| 工程边界与平台 | 依赖方向 `app → feature → domain/core`，数据实现在 `data:*`；新增模块需同步 `checkArchitecture`；Room 走显式 `Migration` + schema 快照 + 升级测试；单 Activity Compose，minSdk 26、targetSdk 37，通知需 API 33+ 运行时权限 | [CLAUDE.md](../../CLAUDE.md)、工程配置 |

```text
app（调度 / 通知 / 装配）
  ├─→ :feature:chat（会话列表、未读、跳转入口）
  ├─→ :domain:generation（Prompt 编译 / 生成执行）
```

## 3. 数据模型与存储

以下字段均为**建议方案**，需在开工时按阶段 1/2 已落地的实际结构确认；标"待定"的项不构成已确认实现。

### 3.1 持久化对象

| 对象 | 建议字段 | 存储位置（待定） | 依据 |
| --- | --- | --- | --- |
| 联系计划 | `planId`、`charFile`、`sessionId`、`worldId`、`plannedWorldTime`、`reason`、`status`、`attemptCount`、`lastResult`、`createdAt`、`updatedAt` | 建议 Room 新表（按 `worldId + status + plannedWorldTime` 查询） | 需要按到期时间查询与恢复；JSON 文件不适合到期扫描 |
| 待回复任务 | 由阶段 2 定义（角色忙碌时暂缓回复的消息） | 阶段 2 既有存储 | 阶段 4 只读取并在后台执行，不重复建模 |
| 联系记录 | `lastUserMessageAt`、`lastProactiveAt`、`nextCheckWorldTime`、`lastReason`、`recentPlanId` | 建议 `:data:settings` 按角色存放 | 数据量小、随角色维护；具体文件/字段待定 |
| 去重键与消息标记 | 消息/通知：`sessionId + planId`；`messages.dataJson` 记 `kind=proactive`、`planId` | Room 唯一约束 + 事务检查；现有 `dataJson` 可免新增列 | 保证 P4-09；具体结构待定 |
| 未读与已读 | 会话未读数、`lastReadAt`（或由消息时间派生） | 待定：阶段 1 会话列表或本阶段 `sessions` 新列 | 现在 `sessions` 表无未读字段（§5）；无论归属，都需显式迁移 |
| 时间锚 | 计划/到期记录以**世界游戏时间**保存；消息与通知仍用真实时间戳 | 沿用阶段 2 双时间记录 | 阶段 2 已约定游戏时间与消息时间分别保存 |

### 3.2 状态机

| 状态 | 进入条件 | 允许的下一步 | 说明 |
| --- | --- | --- | --- |
| 计划中 | 判定产出联系计划 | 到期检查、取消 | 世界切换/故事开始后仍保留，但遵守新状态 |
| 已阻断 | 到期时世界冻结、角色忙碌或场景互斥 | 等待恢复、取消 | 保留计划与原因，恢复后按世界时间继续 |
| 生成中 | 通过执行前检查并开始生成 | 待提交、失败 | 需与用户发送串行化，避免同会话竞争 |
| 待提交 | 生成完成并通过内容检查 | 已完成、失败 | 提交前再次校验世界与场景 |
| 已完成（含通知） | 消息落库事务成功 | 已读/结束、重试通知 | 事务含消息、会话更新时间、计划状态、未读；通知失败不回滚消息但需记录 |
| 已读/结束 | 用户点击通知或进入会话 | — | 清未读、取消通知 |
| 失败 | 生成失败、超时、无模型/网络 | 重试（待定上限）、放弃 | 不留半截消息，对用户不可见 |

### 3.3 事务与幂等

- 提交使用单一 Room `@Transaction`：插入主动消息（`ts` 在锁内重新分配、会话内严格递增）→ 更新会话 `updatedAt` → 更新计划状态 → 递增/写入未读。任何一步失败整批回滚，不允许"消息已存、计划未完成"。
- `planId` 作为幂等键：事务前按 `planId` 查询已提交记录；重复触发直接返回已完成，不进入生成。
- 通知在事务提交后构建；同一 `sessionId + planId` 只允许一个通知。用户打开会话后取消并标读。
- 去重覆盖三个环节（生成、写入、通知），对应 P4-09；重新进入 APP 的恢复流程也走同一幂等检查。

## 4. 接口与关键流程

### 4.1 触发判定

```kotlin
// 建议的纯逻辑形态（:domain:proactive，待确认归属）
data class ProactiveSignals(
    val worldId: String, val isCurrentWorld: Boolean, val isWorldFrozen: Boolean, val gameTime: Long,
    val personality: PersonalityHints, val scheduleBusy: Boolean, val inSameSceneStory: Boolean,
    val lastUserMessageAt: Long, val lastProactiveAt: Long, val memoryHints: List<String>, val modelAvailable: Boolean,
)
sealed interface ProactiveDecision { /* Contact(planId, reason, plannedWorldTime) 或 Skip(reason) */ }
fun evaluate(signals: ProactiveSignals, clock: Clock, random: Random): ProactiveDecision
```

判定要点：

- 仅当前世界参与判定；世界冻结、角色忙碌、同场景线下故事进行中直接跳过并记录原因。
- 联系间隔与主动意愿由角色性格参数化（映射方式待定，见 §9）；林夏与沈言使用同一实现但不同参数，验收看频率差异而非措辞差异。
- 约定、共同经历、日程空隙作为动机与时机来源，注入生成请求，不直接写死话术。
- 时钟与随机可注入，保证判定可复现、可单测；判定结果落计划记录，便于验收记录"联系原因与计划时间"。

### 4.2 生成管线复用

1. 读取到期计划 → 校验当前世界、冻结状态、角色忙闲、场景互斥。
2. 加载会话、角色卡、世界书、预设、近期历史与相关记忆（复用阶段 1/3 的既有加载路径）。
3. 组装主动生成请求：无新用户输入，需覆盖输入内容并注入时间事实与动机块；沿用活人感预设与纯消息规则。
4. 调用现有生成执行器（后台默认非流式，待定），通过纯消息、知情范围与非空检查后才进入提交。
5. 提交事务（§3.3），成功后更新联系记录并触发通知。

### 4.3 后台调度与提交前校验

| 入口 | 职责 | 限制 |
| --- | --- | --- |
| App 内定时检查 | APP 前台时按间隔检查到期计划 | 仅前台运行；与后台入口共用判定与幂等 |
| 系统后台调度 | 关闭 APP 后执行到期计划并发通知 | 具体机制（周期任务/精确闹钟/前台服务）以阶段 2 P2-12 结论为准 |
| 回前台恢复 | 重进 APP 时对账计划、补齐未完成状态 | **不能替代关闭期间的通知**（P4-07）；只能作为恢复与兜底 |

关键流程：

1. 计算当前世界游戏时间（复用阶段 2 推进规则），取出 `status ∈ {计划中, 已阻断}` 且到期的计划。
2. 执行前检查：当前世界、未冻结、角色不忙碌、无同场景故事、模型与网络可用；不满足则写回阻断原因，等待恢复。
3. 生成完成后、提交前再次检查世界与场景（P4-10）；状态已变化则丢弃本次结果并保留/取消计划。
4. 提交成功 → 通知 → 更新联系记录与调度水位。
5. 恢复时对账：已提交计划不重生成；有效未完成计划重新排期；已失效计划取消并留记录。

### 4.4 通知通道与点击跳转

| 项 | 方案 | 状态 |
| --- | --- | --- |
| 渠道 | `proactive_messages`（IMPORTANCE_HIGH，声音/横幅），首次启动创建 | 待实现；渠道创建后 importance 不可程序修改 |
| 权限 | targetSdk 37，API 33+ 需 `POST_NOTIFICATIONS` 运行时权限 | 待实现；当前 Manifest 无该权限 |
| 通知内容 | 角色名 + 已保存消息正文预览；不出现动作/旁白；同一会话按需聚合 | 待定聚合粒度 |
| 点击 | `PendingIntent` 携带 `charFile`（优先）/`sessionId` → `MainActivity`（需 `singleTop`）→ `onCreate`/`onNewIntent` 统一打开目标会话 | 待实现；当前 Manifest 无 `launchMode`，`MainActivity` 无 `onNewIntent` |
| 已读 | 打开会话后清未读并取消对应通知 | 依赖未读存储方案 |
| 失败/免打扰 | 权限被拒或渠道关闭时不阻断生成与落库，应用内未读仍可见并提示系统入口（产品行为待确认）；不提供静默时段、免打扰开关或低打扰渠道降级 | 产品行为待确认 |

### 4.5 任务恢复与幂等

- 冷启动/回前台统一执行对账：恢复有效未完成计划、清理失效计划、校验已提交消息未重复。
- 幂等三层：`planId` 唯一约束；事务前已提交检查；通知 `sessionId + planId` 唯一。
- 世界切换或故事开始后，已有计划遵守新状态；不因重新进入 APP 绕过冻结或场景互斥。
- 失败计划的重试上限、退避与是否补发待定（§9），但任何重试都复用同一幂等入口。

### 4.6 与阶段 2 后台最小验证的衔接

| 阶段 2 验证项 | 阶段 4 复用方式 | 需补齐的差异 |
| --- | --- | --- |
| 真实通知与关闭场景到达 | 复用通知渠道/权限引导路径与 P4-07 场景基线 | 通知内容、聚合、点击跳转与已读；把测试任务换成真实联系计划的生成延迟 |
| 后台运行路径结论 | 决定本阶段调度实现，不再重复选型 | 生成耗时、失败处理、幂等与恢复 |
| 系统强制停止记录 | 直接引用为交付边界说明 | 与普通关闭分开记录，不混入通过标准 |

## 8. 风险/限制/技术债

| 风险/限制 | 影响 | 应对/现状 |
| --- | --- | --- |
| Doze/厂商 ROM 后台限制 | 关闭 APP 期间通知可能延迟或不到，无法承诺准点 | 以实际设备记录验收；引导用户关闭电池优化（依据见[调研文档](调研文档.md)），不承诺 100% 到达 |
| force-stop | 系统强制停止后后台全部失效，直到用户手动打开 | 单独记录为交付边界，不与普通关闭混同 |
| 无服务端 + 生成成本 | 无法远程唤醒；无网络/无模型只能等待或失败；后台生成有超时与 token 成本 | 生成失败不落库，恢复后重试或取消（策略待定）；以性格控制频率、限制重试 |
| 通知权限/渠道被用户关闭 | 无法满足"始终通知" | 提示并引导系统设置；生成与未读不阻断；产品降级行为待确认 |
| 会话并发写 | 用户发送与主动生成竞争 | 串行化 + 提交前状态校验 + 幂等；具体锁机制待定 |
| 游戏时间与真实时间映射 | 关闭期间当前世界如何推进决定到期判定 | 完全复用阶段 2 约定；阶段 2 未定则本阶段无法验收 P4-07 |
| Room 变更与技术债 | 联系计划/未读需迁移，错误迁移影响既有聊天数据；存储位置、未读归属、通知聚合、重试策略、是否新增模块未定 | 显式 `Migration` + schema 快照 + 升级测试；开工前在 §9 逐项拍板 |
| 不做免打扰 | 用户无法静音角色聊天，存在过度打扰风险 | 产品已明确；实现上只靠性格频率与状态约束，不提供开关 |
| 旧调研方案漂移 | 旧设计含 4 档频率、免打扰四件套、WorkManager 15 分钟等，与当前需求不同 | 以[需求文档](需求文档.md)为准，旧方案仅作参考；差异见[调研文档](调研文档.md)§4 |

## 9. 开放问题

| 问题 | 建议/待定 | 影响 |
| --- | --- | --- |
| 是否新增 `:domain:proactive` 模块 | 倾向新增（纯 JVM、可单测）；若新增需同步 `build-logic` 与 `checkArchitecture` | 模块拆分与测试成本 |
| 阶段 2 后台路径最终选型 | 以 P2-12 实测为准；本设计不预设 WorkManager/精确闹钟 | 调度实现与关闭场景验收 |
| 存储位置与未读归属 | 联系计划/记录放 Room 还是 `data:settings`（到期查询倾向前者）；未读由阶段 1 交付或本阶段补 `sessions` 迁移 | 数据迁移、恢复复杂度与相位依赖 |
| 性格到频率/概率的映射 | 角色卡无标准频率字段；需确定用哪些性格信息、如何记录才可验收 | P4-02 可验证性 |
| 主动消息条数、发送节奏与单次请求预算 | 需求未规定；倾向一次生成少量消息、单次请求 | 成本、体验与"不刷屏" |
| 前台通知与聚合粒度 | 前台/当前会话是否仍弹通知；每会话一条 vs 多条，需与未读联动 | 通知体验与 P4-09 判定 |
| 失败/离线/无模型的恢复策略 | 重试上限、退避、是否补发、是否留待下次 | 可靠性边界与用户感知 |
| 多角色同时到期的优先次序 | 需可解释规则（性格/日程/约定优先），避免随机 | 后台一次检查的执行顺序 |
| 通知权限被拒的产品行为 | 提示 + 应用内未读兜底，还是视为未通过 | P4-11 与发布说明 |
