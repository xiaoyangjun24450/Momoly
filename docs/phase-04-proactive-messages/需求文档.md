# 需求文档：阶段 4 主动联系与后台通知

> 角色：产品经理
> 阶段：4 主动联系与后台通知
> 状态：计划，尚未实现和验收
> 更新：2026-11-04
> 文档边界见 [AGENTS.md](../../AGENTS.md)
> 关联：[设计文档](设计文档.md) · [调研文档](调研文档.md) · [文档总览](../README.md) · 前置 [阶段 3 需求](../phase-03-stories-and-memory/需求文档.md) · 后续 [阶段 5 需求](../phase-05-location-expansion/需求文档.md)

## 1. 阶段目标与可体验结果

让角色能够依据性格、日程、记忆和约定主动联系用户，并在用户关闭 APP 后继续执行符合条件的消息任务、发出系统通知。本阶段是"角色主动陪伴"从被动回复转为主动发起的一步，产品规则见[文档总览](../README.md)中的定位与已确认决策。

前置条件：阶段 3 验收通过（线下故事与共享记忆可用），阶段 2 的最小后台通知验证（P2-12）已给出可运行路径与设备记录。

完成后应能实际看到：

- 没有用户新消息时，当前世界的角色在原会话中出现主动消息；会话列表预览与未读状态同步更新。
- 热情的林夏与寡言的沈言联系安排不同，差异可以由性格解释，而不是同一套固定频率。
- 主动消息能引用真实共同经历（如借书），未获知该经历的角色不会引用私人细节。
- 角色忙碌、正在与用户同场景进行线下故事、或所在世界已冻结时，不会有不符合状态的主动消息。
- 用户关闭 APP（退到桌面、锁屏、划掉任务列表分别验证）后，在当前世界收到真实系统通知，点击通知回到该角色唯一会话。
- 普通回复与主动消息都始终通知；APP 内没有免打扰时段或静默开关。
- 重新打开 APP 或反复检查任务时，同一条消息不会重复生成、重复写入或重复通知。

本阶段不负责：其他世界的主动联系或通知、地点拓展与整体交付验收（属[阶段 5](../phase-05-location-expansion/需求文档.md)）、免打扰与静默时段（明确不做）。

## 2. 范围

### 2.1 本阶段交付

| 能力 | 模块 | 一句话范围 |
| --- | --- | --- |
| 主动联系安排与触发 | 9、5 | 依据性格、日程、游戏时间、世界/场景状态、联系记录与记忆判断是否联系、何时联系 |
| 主动消息生成与唯一会话接入 | 6、8、11 | 复用既有生成能力产出角色消息，写入该角色唯一会话，不伪造用户消息 |
| 后台任务执行与状态检查 | 12、3、5 | 不依赖聊天页面保持打开；执行前与提交前都遵守世界、场景和角色状态 |
| 系统通知与会话跳转 | 12、6 | 只对已保存消息发通知；点击进入原会话；始终通知，无免打扰 |
| 联系任务状态与去重 | 9、12 | 重新进入 APP 后任务与会话状态一致，不重复生成/写入/通知 |

### 2.2 本阶段不做

- 不提供免打扰、静默时段、"稍后提醒"或按会话关闭通知；不做低频/高频档位等统一频率设置。
- 不向用户展示内部触发原因、调度时间或提示词细节；验收记录可保存这些信息，但不进入普通界面。
- 不为主动消息另建会话或另造"系统消息"；不通过伪造用户发言来触发生成。
- 不承诺系统强制停止（force-stop）、厂商清理后的到达；这类场景单独记录行为与交付边界，不能与普通关闭混为一谈。
- 不建设独立备份恢复、旧数据迁移或"只提供后台接口"的中间阶段。

## 3. 功能需求

### 3.1 主动联系安排与触发（模块 9、5）

| 项 | 要求 |
| --- | --- |
| 输入 | 角色性格、角色日程与当前活动、游戏时间、当前世界与场景状态、最近联系记录、约定和相关记忆 |
| 输出 | 是否联系、联系原因、计划联系时间、交给聊天生成的请求、后续检查安排 |
| 触发 | 用户不先发消息也能触发；频率由角色卡中的角色性格决定，不使用所有角色统一的固定频率 |
| 优先级 | 世界冻结、角色状态（忙闲）与同场景线下互动限制优先于联系计划；计划被状态阻断时不强行发送 |
| 话题 | 约定、共同经历等为主动消息提供时机和话题；性格决定主动的意愿和密度 |

示例：林夏空闲时愿意分享近况，主动联系较多；沈言寡言，主动联系较少，但临近约定时间也可以主动确认。两人的安排必须能被性格解释，验收时不能只凭措辞差异判定。

验收关注：P4-02（性格影响频率差异可解释）、P4-04（不绕过忙碌状态）。

### 3.2 主动消息生成与唯一会话接入（模块 6、8、11）

| 项 | 要求 |
| --- | --- |
| 生成输入 | 主动联系请求、目标角色、角色记忆、世界状态、原聊天历史 |
| 生成输出 | 与联系原因相关的角色消息、原会话中的新记录、更新的会话预览与未读状态、必要的记忆更新 |
| 会话 | 主动消息与普通回复写入同一个角色会话；一个角色只有一个聊天会话 |
| 生成方式 | 复用阶段 1 已有生成能力，不为主动消息另造一套模型调用或提示词体系 |
| 内容规范 | 沿用线上活人感与纯消息要求；不出现动作、场景、旁白或内心独白；不伪造用户发言 |
| 知情范围 | 内容服从角色实际经历和已知信息，不能引用角色未参与的事件细节 |
| 条数 | 一次主动联系可产生一条或数条消息；条数上限与展示节奏由设计确定（待确认，见 §7） |

示例：林夏在借书后主动发来"你借我的那本红色封面的书我开始看了"，消息出现在林夏原会话里，用户无需先询问；周宁不能凭空提到借书细节。

验收关注：P4-01（主动消息进原会话、无伪造发言）、P4-03（经历与知情范围、纯消息、通知预览一致）。

### 3.3 后台任务执行与状态检查（模块 12、3、5）

| 项 | 要求 |
| --- | --- |
| 运行条件 | 任务不依赖聊天页面保持打开；具体后台运行方式以阶段 2 验证结果为输入 |
| 规则复用 | 后台执行沿用与前台相同的游戏时间、世界冻结、角色日程与场景规则，不单独维护一套简化规则 |
| 执行前检查 | 世界已冻结、角色状态不允许、场景互斥时不得执行联系或生成 |
| 提交前检查 | 生成完成、准备提交时再次检查世界与场景；期间切换世界或进入同场景线下故事，结果不得作为该世界的新消息提交或通知 |
| 恢复 | 冻结世界恢复后，依据保存的世界时间与计划继续；未完成的有效任务可继续，已发出的不重复发送 |
| 关闭 APP 期间 | 关闭期间当前世界的游戏时间推进方式由阶段 2 的时间规则决定，本阶段直接复用 |

示例：用户关闭 APP 后，校园世界的林夏在空闲时处理一条到期联系；若用户已切换到奇幻世界，校园时间冻结，该任务不能继续产生消息，返回后按原世界时间继续调度。

验收关注：P4-06（跨世界冻结）、P4-07（关闭场景）、P4-10（提交时状态仍生效）。

### 3.4 系统通知与会话跳转（模块 12、6）

| 项 | 要求 |
| --- | --- |
| 通知对象 | 仅对已经保存成功的角色聊天新消息发通知；不为草稿、未提交生成结果或另行生成的第二条消息发通知 |
| 内容 | 带角色名称与消息预览；预览是消息正文，不出现动作、场景或旁白 |
| 免打扰 | 本阶段不提供免打扰功能；普通回复与主动消息的聊天新消息都按始终通知处理 |
| 世界范围 | 只有当前世界的角色消息会产生通知；冻结世界不产生通知 |
| 点击 | 点击通知进入对应角色的既有会话，能看到同一条消息和此前聊天历史；不创建新会话，不落到默认会话 |
| 权限 | 目标设备需允许通知；权限被拒或渠道被关闭时的降级行为必须记录并说明（待确认，见 §7） |
| 归并 | 同一会话的多条新消息不应产生互相矛盾的多条通知状态；同一消息不重复通知 |

示例：锁屏收到"林夏：你现在方便吗？"的通知，点击后打开林夏原会话，能看到同一条消息和此前聊天记录。

验收关注：P4-07（分场景真实通知）、P4-08（原会话跳转）、P4-11（始终通知、无免打扰）。

### 3.5 联系任务状态与去重（模块 9、12）

| 项 | 要求 |
| --- | --- |
| 状态保存 | 联系安排、执行结果、待继续任务与消息落库状态可持久化，重新进入 APP 后一致 |
| 重新进入 | 继续未完成的有效任务；已发出并保存的消息不因重新加载而再次生成或重复写入 |
| 世界/故事变化 | 世界切换或故事开始后，已有计划遵守新的状态；不能借重新进入 APP 绕过冻结或场景互斥 |
| 去重范围 | 生成、写入、通知三个环节都不重复；反复打开 APP 或反复检查任务不产生第二条消息、第二条通知 |
| 失败处理 | 生成失败、状态失效、模型不可用等不能留下半截消息或错误气泡；失败结果对用户不可见，并可被记录 |

示例：林夏的消息已经收到并保存，用户反复从通知栏和桌面打开 APP，聊天记录中始终只有这一条消息，通知状态也一致。

验收关注：P4-09（不重复）、P4-10（提交时状态校验）。

## 4. 跨模块约束

| 约束 | 规则 | 关联验收 |
| --- | --- | --- |
| 频率由性格决定 | 不套用所有角色统一的固定联系频率，也不以统一档位代替性格差异 | P4-02 |
| 仅当前世界可联系/通知 | 其他世界保持冻结，不主动发消息、不产生通知；返回后从冻结点继续 | P4-06 |
| 世界冻结优先 | 计划、生成、提交三段都以提交时世界状态为准；冻结后不产生新消息 | P4-06、P4-10 |
| 同场景线下互动优先 | 正在与用户进行同场景线下互动的角色不同时从聊天窗口发消息；故事状态约束主动联系 | P4-05 |
| 日程/忙闲状态优先 | 忙碌角色不绕过状态即时联系或回复；到允许时段后可以联系，重复检查不重复发 | P4-04 |
| "关闭 APP"分场景验收 | 退桌面、锁屏、划掉任务列表分别记录；系统强制停止单独记录；不得以重新打开后补发代替关闭期间通知 | P4-07 |
| 不提供免打扰 | 不设静默时段、会话免打扰、通知开关替代品；聊天新消息始终通知 | P4-11 |
| 通知只针对已保存消息 | 通知与落库事务结果绑定；点击看到的消息必须是已保存的那一条 | P4-08、P4-09 |
| 线上纯消息边界 | 主动消息沿用阶段 1 活人感与纯消息规则；动作、场景、旁白只属于线下故事 | P4-03 |
| 一个角色一个会话 | 主动消息复用原会话，不新建会话、不伪造用户消息 | P4-01、P4-08 |

## 5. 验收用例与通过标准

准备：目标设备已允许通知；模型服务可用；按阶段 2 的时间规则安排可到期任务。主动联系用例使用实际性格和日程规则；验收记录可保存联系原因与计划时间，但不要求把这些信息展示给普通用户。

| 编号 | 操作步骤 | 应看到的结果与通过标准 |
| --- | --- | --- |
| P4-01 | 保持当前世界运行，不发送用户消息，等待或推进到联系时机。 | 角色主动消息出现在原会话，会话列表和未读状态更新；没有伪造的用户发言。 |
| P4-02 | 在可比较的空闲时间内观察林夏与沈言的联系安排和实际结果。 | 性格实际影响安排，记录能解释两者差异；不能仅凭一次随机回复认定性格控制已生效，也不以措辞不同代替频率差异。 |
| P4-03 | 完成借书故事后，让相关联系任务到期。 | 主动消息能使用真实借书经历；未获知此事的角色不会引用私人细节；聊天气泡与通知预览都是消息正文，没有动作或旁白。 |
| P4-04 | 在角色忙碌时触发检查，再推进到其允许回复的时段。 | 消息不绕过角色状态；到合适时机可以联系或回复，重复检查不生成重复消息。 |
| P4-05 | 让林夏参与线下故事，再触发主动联系检查。 | 林夏不会同时从聊天窗口发消息；同场景其他角色遵守相同规则。 |
| P4-06 | 切换到奇幻世界，让校园角色原计划的时间在现实中经过。 | 校园时间保持冻结，校园角色没有新消息和通知；返回校园后按原世界时间继续调度。 |
| P4-07 | 分别退到桌面、锁屏、划掉任务列表，等待有效任务到期。 | 按目标交付场景收到真实角色消息通知；每个场景单独记录设备、条件、实际延迟与结果，不能以重新打开 APP 后才补发代替关闭期间的通知。 |
| P4-08 | 点击一条通知。 | 进入对应角色的唯一会话，消息已存在，原聊天历史保留，不创建新会话。 |
| P4-09 | 收到通知后多次重新打开 APP 或触发任务检查。 | 消息没有重复生成、重复写入或重复通知；会话和任务完成状态一致。 |
| P4-10 | 主动生成进行中切换世界，或使目标角色进入同场景故事。 | 生成结果在提交时仍受当前状态限制，不能在已冻结世界或被暂停的聊天中继续发出。 |
| P4-11 | 分别接收普通角色回复和主动消息，检查通知设置。 | 两类聊天新消息都遵守始终通知要求；APP 没有免打扰时段或静默开关。 |

通过标准：主动联系真实受性格、日程、记忆和世界状态控制；约定的关闭场景能收到通知并回到原会话。未完成的后台场景必须保留为未通过项，不能用重新打开后的补发结果替代。

## 6. 交付物

- 主动消息、会话列表预览与未读状态、系统通知、通知跳转的截图或录屏。
- 各关闭场景（退桌面、锁屏、划掉任务列表、系统强制停止）的设备、系统版本、运行条件、实际延迟与结果记录。
- 性格影响联系安排、状态阻止不合适联系、消息不重复的验证记录。
- P4-01 至 P4-11 的实际结果，以及阶段 1～3 关键路径回归结果。
- 阶段 2 后台最小验证结论在本阶段的实际复用说明（采用了哪条运行路径、哪些差异未解决）。

## 7. 依赖与待确认问题

### 7.1 依赖

| 依赖方 | 需要的前置能力 | 不满足时的后果 |
| --- | --- | --- |
| 阶段 1 | 唯一会话、聊天生成、消息落库、纯消息与活人感规则 | 无法按"原会话接入"验收 P4-01、P4-03、P4-08 |
| 阶段 2 | 游戏时间规则、世界冻结与恢复、角色日程与忙闲、后台最小通知验证 | 无法判断何时到期、无法按世界约束检查、无可用后台路径 |
| 阶段 3 | 共享记忆、知情范围、同场景故事互斥 | 主动消息无法使用真实经历，P4-03、P4-05 无法通过 |
| 工程现状 | 会话列表预览与未读、通知点击入参与后台能力尚未实现（见[设计文档](设计文档.md)§5）；基础会话列表与生成已存在 | 需在本阶段补齐，不能假定已存在 |

### 7.2 待确认问题

| 问题 | 为什么需要确认 | 建议归属 |
| --- | --- | --- |
| "关闭 APP"必须通过的场景集合 | 退桌面、锁屏、划掉任务列表、force-stop 的交付边界影响验收结论与发布说明 | 阶段 2 验证后由产品拍板 |
| 通知权限被拒/渠道被关闭时的产品行为 | 产品要求"始终通知"，但系统权限可能关闭；需明确是提示、降级为应用内未读，还是视为未通过 | 本阶段开工前 |
| APP 在前台或当前会话时是否仍弹系统通知 | "始终通知"是否覆盖前台场景；旧设计为前台不发通知，当前需求未明确 | 产品确认 |
| 一次主动联系的条数上限与发送节奏 | 影响体验与"不重复/不刷屏"的判定，当前需求未规定具体条数 | 设计阶段提出，产品确认 |
| 是否需要任何用户可见的主动联系开关 | 本阶段明确不做免打扰，但是否提供"暂停主动联系"类开关尚未确认 | 产品拍板 |
| 多角色同时到期的优先次序 | 后台一次检查可能命中多名角色，需要可解释的先后规则；当前需求未规定 | 设计与产品共同确认 |
