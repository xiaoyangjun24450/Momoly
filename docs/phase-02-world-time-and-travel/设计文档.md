## 1. 目标与约束

设计目标：在不改动 `chats.db` schema、不破坏 SillyTavern 导入导出兼容的前提下，新增“世界运行状态 + 游戏时间 + 出行行程 + 角色日程/位置”的可保存实现，并完成后台通知路径的最小验证。

现状基线（代码事实，截至 2026-11-04）：

| 事实 | 证据/位置 | 对本阶段的影响 |
| --- | --- | --- |
| 世界状态目前是占位实现 | `:core:model` 的 `data/world/WorldContext.kt`：`WorldContext(isPlaceholder=true)` 固定“家/08:00”，`ChatContent` 直接使用 `PlaceholderWorldContextProvider` | 本阶段用真实实现替换 provider，接口签名可保留 |

## 3. 数据模型与存储

### 3.1 模型草案（字段为设计草案，未落代码）

| 模型 | 关键字段 | 说明与状态 |
| --- | --- | --- |
| `WorldRuntime` | `schemaVersion`、`runningWorldId`、`worlds: Map<worldId, WorldState>`、`lastSavedAt` | 全局单文档；`runningWorldId` 是冻结规则的单一事实源 |
| `WorldState` | `worldId`、`name`、`gameMinutes: Long`、`userPlaceId`、`userTrip: Trip?`、`characters: Map<charFile, CharacterWorldState>`、`updatedAt` | 每个世界各自保存；`gameMinutes` 为绝对游戏分钟，显示时取 `% 1440` 得 HH:mm；是否引入日期待定 |
| `Place` | `id`、`worldId`、`name`、`tags`、`openHours?`、`sourceRef` | 由世界书转换；字段来源与转换规则待调研 |
| `TravelOption` | `fromPlaceId`、`toPlaceId`、`mode`（步行/骑行…）、`durationMinutes`、`sourceRef` | 只从世界书读取，不估算；双向路线缺省处理待定 |
| `Trip` | `id`、`fromPlaceId`、`toPlaceId`、`mode`、`durationMinutes`、`elapsedMinutes`、`status(ON_ROAD/ARRIVED)`、`startedAtGameMinutes` | 用户行程；“路上”状态由 `status` + 剩余时间表达 |
| `CharacterWorldState` | `charFile`、`placeId`、`activity`（忙碌/空闲/移动）、`activityLabel`、`movingTrip: Trip?`、`replyPolicy(AVAILABLE/BUSY)`、`updatedAt` | 展示与回复判定共用，避免位置/活动不一致 |
| `ScheduleEntry` | `charFile`、`kind(STAY/MOVE)`、`startGameMinutes`、`endGameMinutes`、`placeId`、`fromPlaceId/toPlaceId?`、`activityLabel`、`busy` | 日程来源与格式待调研；`MOVE` 段必须消耗路线耗时 |
| `WorldContext`（既有） | 现有字段 + `isPlaceholder=false` | 阶段 1 接口直接复用，不作为持久化模型 |

明确“待定”项：日程从哪里来（角色卡/世界书/内置模板/验收样例）与格式；世界书到 `Place`/`TravelOption` 的转换方式；游戏时间是否需要日期与跨日展示；待回复消息是否需要独立存储（倾向不新增，按消息时间与角色可用性推导）。

### 3.2 存储方案

| 数据 | 位置 | 形式 | 版本/说明 |
| --- | --- | --- | --- |
| 运行世界、世界时间、用户位置与行程、角色状态、日程 | `filesDir/world/state.json` | 单文档整体读写，临时文件 + rename 原子替换 | `schemaVersion=1`；数据量小（几十世界×几十角色）；量大后再评估拆分为 `world/<worldId>.json` |
| 地点与路线 | 随 `state.json` 缓存，来源仍为世界书 | 导入/读取时转换 | 不以副本替代世界书；世界书变更需重建（刷新规则待定） |
| 消息时间戳 | `messages.ts`（Room，既有） | 现实毫秒，严格递增 | 不改 schema、不改语义；与游戏时间无换算关系 |

不扩展备份：按“取消独立保存/恢复/迁移模块”的决策，`world/state.json` 不进入备份 section，换机或清数据不保证恢复；这是已知限制（见 §8）。写入并发用 app 级单例 `Mutex` 串行化“推进时间 / 出发与到达 / 切换世界 / 保存快照”，后台最小验证若走 Worker 也复用它（WorkManager 默认同进程待核实）。

## 4. 接口与关键流程

### 4.1 领域接口草案（设计用，不是已定实现）

```kotlin
// :domain:world（纯 JVM，草案）
data class AdvanceResult(val runtime: WorldRuntime, val transitions: List<WorldTransition>)

interface WorldTimeEngine {
    fun advance(runtime: WorldRuntime, targetWorldId: String, deltaMinutes: Long): AdvanceResult
    fun switchWorld(runtime: WorldRuntime, toWorldId: String): WorldRuntime
}

class TravelEngine {                       // 出发 / 推进 / 到达，纯状态机
    fun start(world: WorldState, toPlaceId: String, mode: String): WorldState
    fun advance(world: WorldState, deltaMinutes: Long): WorldState
}

class ScheduleResolver {                   // 某角色在某一游戏分钟的位置/活动/可回复性
    fun resolve(world: WorldState, charFile: String, minute: Long): CharacterWorldState
}

// :data:world（Android，草案）
interface WorldStateRepository {
    suspend fun load(): WorldRuntime
    suspend fun save(runtime: WorldRuntime)
}
```

### 4.2 游戏时间推进

1. 校验目标世界为当前运行世界，否则拒绝推进（冻结世界只能被切换，不能被推进）。
2. 取本次推进量（用户选择 10/30 分钟等，单次上限待定）；按“下一次状态变化时刻”（行程到达、日程条目边界）分片。
3. 逐片推进时间并应用该时刻的状态变化：行程到达、角色位置/活动切换；分片内不改变状态。
4. 全部应用后整体落盘并刷新 `WorldContext`；同一时刻的多个变化按确定顺序应用（建议：行程到达 > 日程切换 > 其他，最终顺序由待确认项定稿）。
5. 结果幂等：状态完全由“当前游戏时间 + 行程 + 日程”推导，重复推进不会重复产生行程或重复切换。

未手动加速时的推进规则（待确认，建议方案 A）：A 纯手动推进（默认，验收可重复）；B 现实时间等比映射并在回前台补算；C 混合。方案 B/C 需要额外定义换算比例、离线补算上限与验收方法，建议阶段 2 先按 A 实现，保留 `advance` 入口以便替换。

### 4.3 跨世界冻结与恢复

1. 切换时保存当前世界状态（时间、用户位置、行程进度、角色状态与日程游标）；`runningWorldId` 改为目标世界。
2. 目标世界直接恢复其保存的 `gameMinutes` 与状态，不补算离开期间的时间，也不产生移动耗时。
3. 冻结世界：拒绝推进；聊天发送/回复入口返回“世界未运行”；角色日程、移动、待回复处理全部暂停。
4. 返回后从冻结点继续；界面立即刷新为真实时间与位置。

与生成并发（对应 P2-09）：切换世界时取消或拦截该世界未完成的生成；消息提交前校验 `runningWorldId` 与角色状态，不一致则丢弃本次生成结果，不写入、不通知。已完成的消息保留；返回后按保存的调度规则决定是否继续，不自动重发。

### 4.4 移动状态机

| 当前状态 | 事件 | 结果 |
| --- | --- | --- |
| 空闲（在 `placeId`） | 选择目标与方式出发 | 创建 `Trip(status=ON_ROAD, elapsed=0)`，位置仍为出发地 |
| 路上 | 推进 Δ 分钟（Δ < 剩余） | `elapsed += Δ`，剩余时间减少，状态不变 |
| 路上 | 推进 Δ 分钟（Δ ≥ 剩余） | 到达目标地点，`status=ARRIVED`，用户位置更新为目标地点，行程结束 |
| 路上 | 切换世界 | 行程保持，随世界冻结；返回后继续 |
| 路上 | 收发聊天消息 | 允许；不改变 `elapsed`、不触发到达 |
| 路上 | 二次出发/改道/取消 | 本阶段不支持（进入前需重新出发） |

### 4.5 到期事件与忙闲回复

用户消息仍走现有链路立即落盘（`SendChatMessageUseCase` 语义不变）。角色是否回复由 `ScheduleResolver` 判定：

1. 世界冻结或角色处于线下故事（阶段 3 接入）→ 不回复。
2. 角色忙碌 → 暂缓：不发起生成，等待下一个空闲边界。
3. 推进到角色空闲 → 处理该会话的待回复消息；以“最后一条消息时间 + 已处理水位”判定，避免重复回复。
4. 角色移动中按“是否可回复”的策略处理（验收素材中移动段按忙碌处理，最终规则待确认）。

本阶段不建独立事件表：待回复处理由“游戏时间推进到空闲边界”驱动；若阶段 4 的跨重启到期任务需要，再引入持久化事件队列。

### 4.6 后台通知最小验证

验证目标只有一条：选定一条可实际执行的通知路径，并记录各运行场景的真实结果，供阶段 4 采用。测试任务与角色主动联系策略无关。

| 候选路径 | 验证内容 | 已知限制 |
| --- | --- | --- |
| 进程内定时（Handler/协程）+ 通知 | 前台与退后台时到达 | 进程被杀即失效 |
| WorkManager 一次性任务（initial delay） | 退后台、锁屏、划掉任务列表后的到达 | 周期最小约 15 分钟且不保证准时，Doze/ROM 会延后 |
| AlarmManager + 广播接收器 | 到期触发通知 | 精确闹钟需用户授权（Android 12+），政策待核验 |
| 回前台补算 | 离线期间任务的补发 | 不证明“关闭期间通知到达”，只能作为降级方案 |

场景记录模板：`场景 / 设备与系统 / 到期方式（渠道/延迟）/ 实际到达时间 / 是否可见 / 结论 / 待解决差异`。系统强制停止（Force stop）通常使闹钟与后台任务失效，作为独立场景记录，不作为普通关闭的通过依据。

### 4.7 阶段 1 占位状态替换

实现 `WorldContextProvider` 的真实版本（读取 `WorldRuntime` 快照，`isPlaceholder=false`），替换 `ChatContent` 与 `HomeScreen` 中的 `PlaceholderWorldContextProvider`；接口签名不变。相关 Robolectric 测试（`HomeScreenTest`、`WorldProfileEditorTest` 使用占位 provider）需同步改为注入真实/假状态。阶段 1 “占位值不作为真实状态注入模型”的约束在替换后仍成立：本阶段只展示，不注入 prompt。

## 8. 风险、限制与技术债

| 风险/限制 | 影响 | 缓解 |
| --- | --- | --- |
| 游戏时间与现实时间双时钟 | 消息排序、界面显示与规则判定易混用 | 明确“时间只用于展示与规则、`ts` 只表示真实收发”；代码中不互相推导 |
| 时间推进规则未定 | P2-11 等用例不可重复 | 先按纯手动推进实现并记录；规则定稿后只替换入口 |
| 日程来源未定 | 角色位置/活动无法落地 | 先用验收样例日程驱动模型；不预设角色卡字段 |
| 世界书无结构化路线 | 解析失败或耗时缺失 | 转换失败时不编造耗时；给出可理解状态并记录缺失数据 |
| 单文档 `state.json` 并发写 | 进度丢失或半写 | 原子替换 + 单进程 `Mutex`；后台路径若跨进程需重新评估 |
| 切换世界与生成并发 | 冻结世界仍提交消息（P2-09） | 提交前校验 `runningWorldId`；切换时取消/丢弃未完成结果 |
| 后台不可靠 | 通知延迟或不达 | 阶段 2 只验证路径不承诺准时；场景分别记录；阶段 4 定稿交付边界 |
| `targetSdk 37` 通知/精确闹钟政策未核验 | 权限与渠道行为可能不同 | 开工前查官方文档并在目标设备实测 |
| 占位 provider 替换影响既有测试 | 阶段 1 首页/聊天测试可能失败 | 同步改测试注入；单独提交重构并跑现有测试 |
| 不扩展备份 | 换机/清数据丢世界进度 | 已知限制；若产品要求再评估，不与“取消备份模块”决策冲突前先确认 |
| 不改 Room schema | 无法按游戏时间查询/排序历史 | 当前无需求；触发条件为需要历史回放或统计时再评估 v16 迁移 |
