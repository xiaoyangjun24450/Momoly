## 3. 各模块证据、取舍与最小验证

### 3.1 时间、冻结与离线补齐

**源码事实**：AI Town 的 `runStep` 按输入时间推进多个 tick，再保存当前时间、输入处理序号和世代号；后续加载检查世代，避免旧调度继续修改新状态。它依赖 Convex，并有每步工作量限制。见 [AI Town 引擎源码](https://github.com/a16z-infra/ai-town/blob/8e05997f2409275669c8344b84a51692e83f3f33/convex/engine/abstractGame.ts)、[AI Town 架构说明](https://github.com/a16z-infra/ai-town/blob/8e05997f2409275669c8344b84a51692e83f3f33/ARCHITECTURE.md)。

**平台事实**：[Android SystemClock](https://developer.android.com/reference/android/os/SystemClock) 区分可被校时的墙上时间与开机以来的单调时间；`elapsedRealtime` 包含深睡眠，但设备重启后重新计起。后台无回调不妨碍重开时计算差值，不能仅靠 `delay` 次数累计世界时间。

**建议**：记录当前世界、已结算游戏时刻、现实时间锚点和结算进度；同次开机的间隔优先使用单调时钟，跨设备重启需校验持久锚点。正常流逝乘 3，休息附加明确的游戏时长。按“下一个日程/天气/联系事件”的边界结算，避免把 60Hz 小镇循环照搬成离线逐帧模拟。

同刻事件次序和跨世界切换需确定；网络生成在锁外完成，提交时检查世界/事件版本。长离线可以分批处理，不能用 AI Town 的每步上限当成截断游戏经过量的许可。补算过程中生成内容会影响之后日程/关系时，需要按因果顺序保存，不可拿结束时的状态生成所有历史留言。

**验证**：现实 10 分钟→游戏 30 分钟；A→B→A 不偷跑；杀进程后恢复同一段只处理一次；跨午夜；生成过程中切世界；设备时间前调/后调与设备重启。上游没有实现本产品“仅当前世界 3:1、其他世界冻结”的完整现成合同。

### 3.2 休息时钟与多条留言

[Compose 绘图](https://developer.android.com/develop/ui/compose/graphics/draw/overview) 提供 Canvas/DrawScope；[值动画](https://developer.android.com/develop/ui/compose/animation/value-based) 提供循环动画和数值动画。项目已经依赖 Compose，无需为了时钟新增视频、WebView 或动画框架。

**建议**：快钟是加载反馈，结束条件由结算完成决定。指针可以持续快走，但日期/目标时间与实际任务进度要分开，不能动画结束就假报成功。完成后将期间消息按发生顺序发布到原会话，正常新消息继续现有分段节奏。多角色结果的弹出形式仍待界面设计。

**验证**：慢模型、无网、部分完成后重启，时钟不会卡成“已完成”；已落消息不会再播放一次；休息期间不能生成虚构用户发言。这里没有引入第三方时钟依赖的必要。

### 3.3 地图

[MapCompose 用法与瓦片要求](https://github.com/p-lr/MapCompose/blob/87eb12e53d779e1b2700a5734885755d99f71b59/Readme.md) 和 [MapState 源码](https://github.com/p-lr/MapCompose/blob/87eb12e53d779e1b2700a5734885755d99f71b59/mapcompose/src/main/java/ovh/plrapps/mapcompose/ui/state/MapState.kt) 证明 MapCompose 提供瓦片图、缩放、拖拽、标记和路径。它适合已有地图图像/瓦片的场景；不会从世界书文字自动生成地点、路径和耗时。源码已读，未验证与本项目 Compose BOM 的编译及设备表现。

**比较**：地点数量不大、只需名字和头像时，现有 Compose Canvas + 可点击节点最轻；需要大型底图/多级缩放时，MapCompose 为可直接评估的 Kotlin 库。不要为虚构地点引入 GPS、真实地理坐标或在线地图服务。

**建议**：地点用稳定编号、显示名称、说明及可选区域/排布坐标；人物显示读取实际状态。坐标只负责显示，移动耗时来自世界设定。角色走路的中间状态不等于本阶段开放用户出行。

**验证**：多个角色同地可辨认；地点改名引用仍有效；地图与鉴定一致；世界切换不残留原角色；缩放点击与长列表性能。地图布局、用户初始位置来源和冲突合并需设计定稿。

### 3.4 导入校验、地图条目与初始字段

[Character Card V3 规范快照](https://github.com/kwaroran/character-card-spec-v3/blob/f3a86af019fbd99f788f7a1155f399655b34ab35/SPEC_V3.md) 明确应用专用数据放在 `extensions`，并定义卡、世界书和条目各自的扩展位置。该规范未提供本项目所需的世界地图、角色游戏初始时间和入场背景协议；`creation_date` 是卡创建时间，不能拿来当游戏开局时间。

[JsonSchema 校验入口源码](https://github.com/OptimumCode/json-schema-validator/blob/c2679d3bd465ee72b31b07b624b5af44cfc11fd5/json-schema-validator/src/commonMain/kotlin/io/github/optimumcode/json/schema/JsonSchema.kt) 实现对 kotlinx.serialization 的 `JsonElement` 校验并收集错误；[校验库使用说明](https://github.com/OptimumCode/json-schema-validator/blob/c2679d3bd465ee72b31b07b624b5af44cfc11fd5/README.md) 列出 JVM/多平台支持。本轮读取了代码和许可证，未在本项目构建，因此只列为可引入候选。

**建议**：用专用类型标记/命名空间承载结构化数据，保留普通世界书可读文本；地图独立于关键词激活，不应用户聊到“地图”时才存在。两种实现选择：少量稳定字段使用现有解析器+显式校验；若需要作者可用的统一 Schema，再评估上述库。Schema 可检查形状，地点存在、编号唯一、路线端点有效、初始位置有效仍需业务检查。

不要把自动背景适配当成填补必填字段的兜底，也不能让模型自动补缺失地图。目标世界已有地图才可以复用。未确认的字段要求不直接变成拒绝门槛。

**本地缺口**：`WorldBookParser` 将已知字段映射到类型，`WorldBookRepository`/`WorldBookSerializer` 负责保存/导出；需要验证新命名空间在所有编辑、保存、角色导出路径中保留，不能只看原 JSON 存在就声称支持。

**验证**：缺图拒绝、复用已有图、错误精确定位、导入取消无残留、导入→编辑→导出→再次读取仍有专用字段、相同显示名不错误合并。

### 3.5 日程与忙闲回复

[Generative Agents 日程与背景更新源码](https://github.com/joonspk-research/generative_agents/blob/fe05a71d3e4ed7d10bf68aa4eda6dd995ec070f4/reverie/backend_server/persona/cognitive_modules/plan.py) 包含日计划、小时计划、活动时长分解、插入活动后的局部计划重建；[角色状态与日程存储](https://github.com/joonspk-research/generative_agents/blob/fe05a71d3e4ed7d10bf68aa4eda6dd995ec070f4/reverie/backend_server/persona/memory_structures/scratch.py) 保存日程及当前活动。`f_daily_schedule` 使用活动与持续分钟数，适合参考时间段表达。

上游是 Python 研究实现，计划、位置选择、对话和背景修订会多次请求模型；在所读新一天分支还存在待改进注释。不能因此称为成熟的 Android 日程 SDK。

**建议**：在必要时生成一天或一段日程，先校验时段/地点/移动，再由本地规则判断当前忙闲。约定只重排受影响的后续片段。已有角色卡无明确日程时如何生成仍为产品建议，需要确认后落实。延期回复保存“哪些用户消息仍未处理”，与主动消息协调，不让页面关闭丢掉待答内容。

**验证**：跨午夜区间、活动空档/重叠、移动时间不足、预约冲突、提议与正式约定的区别、忙时短回后再跟进、用户连续留言、生成失败重试。不要把所有忙碌统一成绝不回复，用户明确允许简短/敷衍回复。

### 3.6 主动聊天

[Ashley 主动联系决策源码](https://github.com/alpaim/ashley/blob/c2e0c0b5563773c80a5d2acc0c5fb007c04e4212/src/proactive/decision.rs) 将日程、情绪、最近对话、最近主动内容等输入联系决策；[Ashley 联系调度源码](https://github.com/alpaim/ashley/blob/c2e0c0b5563773c80a5d2acc0c5fb007c04e4212/src/proactive/scheduler.rs) 将决策/发送时机拆开。它是 Rust 伴侣系统，存在最短间隔、待发上限和模型决策调用。可参考输入组织，不照搬其限额、现实时间或常驻循环。

[Extension-Idle 源码](https://github.com/SillyTavern/Extension-Idle/blob/4225ff5d5078e4fc583d3e92d3cf78f487da715c/index.js) 使用 `setTimeout`，并在忙于生成时暂缓；部分路径将提示放进输入框或发送叙述消息。这证明空闲触发机制可用，但与本项目世界时间、离线补齐、多角色和“不伪造用户消息”要求不完全一致。

**建议**：先用本地世界/日程/事件过滤联系机会，再在有意义的时机调用现有模型管线；记录原因、发生时间、世界版本和唯一事件标识。决策可以输出联系意图及待发送内容，具体是否合并模型请求由提示合同和质量验证决定，不能预先承诺零额外调用。主动与延期回复按同会话串行协调。

**本地关键缺口**：`ChatReplyScheduler` 只有一个 `active` 回合，草稿和队列在内存中；当前生命周期依赖聊天 ViewModel。不能直接给它加几个定时器就声称支持多角色离线接续。需让世界/任务协调不依赖某个聊天页，继续复用消息生成和分段发布。

**验证**：不打开角色聊天页也可收到；同世界多角色互不取消；正在打字的用户插话优先；重复触发只发布一次；长休息能多轮留言而不反复同一句问候；没有系统通知权限依赖。

### 3.7 天气

[Cataclysm-DDA 天气生成源码](https://github.com/CleverRaven/Cataclysm-DDA/blob/e26bd151399ccac342e0411545e061f1161318e0/src/weather_gen.cpp) 中温度结合地点、游戏时间、季节和种子计算，适合参考“同一时空取同一状态”的组织方式；但风速/风向分支还调用随机函数并使用静态状态，不能把整个天气实现宣传为无状态确定性函数。[天气测试源码（未运行）](https://github.com/CleverRaven/Cataclysm-DDA/blob/e26bd151399ccac342e0411545e061f1161318e0/tests/weather_test.cpp) 存在相关测试，本轮未执行。

该项目为 C++ 生存游戏，主许可证声明 CC BY-SA 3.0，且附带组件另有许可证。这里只参考机制，不把整套源码、常量或素材搬进 Kotlin，也不假定其许可与本项目可直接合并。

**建议**：若采纳模拟天气，用世界气候规则+游戏时间段+持久随机种子生成少量天气类型，记录切换时刻。已处理的时段不重新抽签；天气改变活动必须先通过日程规则。现实天气服务与虚构世界/加速时间不匹配，本轮不推荐接入。

**验证**：同地区同刻一致，分次推进与整段推进一致，重开不随机变天，冻结世界不变，特殊气候设定不被通用模板覆盖。天气粒度与影响幅度仍需产品确认。

### 3.8 好感度与心情

**2026-11-07 追加核验**：用户已确认“长期未回复引起焦虑、烦躁、关系下降并减少主动”的方向，现行产品边界以[需求第 10 节](需求文档.md#10-好感度与心情)为准。下面原有建议保留为历史依据，不能覆盖新决定。实施采用本项目 Kotlin 规则，不复制候选代码，也不新增服务。

- Ashley（核验时 1 Star，MIT，Rust/SQLite，默认分支最近提交北京时间 2026-08-04）适合参考[关系衰减](https://github.com/alpaim/ashley/blob/c2e0c0b5563773c80a5d2acc0c5fb007c04e4212/src/relationship/dimensions.rs)和[未回复分析](https://github.com/alpaim/ashley/blob/c2e0c0b5563773c80a5d2acc0c5fb007c04e4212/src/proactive/ghosting.rs)。限制：未回复分析没有直接保存焦虑/烦躁数值，检测使用创建而非实际送达时间；关系衰减在用户回来时补算，并含按互动次数加分的规则，不照搬。
- companion（2 Star，AGPL-3.0-or-later，Python/SQLite，最近提交 2026-11-07）已接入[未回复阻止后续联系、迟回/短回复降低主动程度](https://github.com/kzndotsh/companion/blob/7a2bd1cd889f84586d63b2d39a197da9d55ad741/src/companion/features/reach/gate.py)，并[学习用户时间习惯](https://github.com/kzndotsh/companion/blob/7a2bd1cd889f84586d63b2d39a197da9d55ad741/src/companion/core/rhythm.py)。限制：其情绪规则明确排除沉默带来负面影响；短回复统计按英文空格，不适合直接用于中文。仅参考控制思路。
- Chitrika（4 Star，MIT，Python/FastAPI/SQLite 与 React/Electron，最近提交 2026-08-12）提供[时间叠加孤独感](https://github.com/UnknownUser03393/Chitrika/blob/8f50e395b765d4d6f5077007da9b4a27f4f5448e/src/chitrika/utils/emotion_algorithms.py)。限制：更孤独更倾向主动，缺乏逐渐退缩；README 的关系随时间衰减描述与当前关系源码不完全一致。

三个候选的原部署均为中等难度（编译或运行环境、模型配置、渠道/前后端），算法移植低至中等成本，整套接入 Android 成本高。本次为联网源码、依赖和许可证核验，未部署候选项目；均非完整覆盖需求的成熟组件。Star 和提交日期仅为核验快照。

[Ashley 关系状态源码](https://github.com/alpaim/ashley/blob/c2e0c0b5563773c80a5d2acc0c5fb007c04e4212/src/relationship/state.rs) 将关系类型、多个关系维度、事件和阶段分开；`apply_event` 处理事件，另有 `apply_neglect`。[Ashley 情绪状态源码](https://github.com/alpaim/ashley/blob/c2e0c0b5563773c80a5d2acc0c5fb007c04e4212/src/emotional/state.rs) 存在情绪基线、强度、描述与按间隔向基线回落的函数。源码还含英文词语/标点启发式估算，不能直接作为中文情绪准确识别器。

[BRING 关系数据模型](https://github.com/Eva-E1/BRING/blob/e907dee1b2a52c023210e5e23be95c6f08fa16f1/world_core/romance/models.py) 与 [BRING 关系更新源码](https://github.com/Eva-E1/BRING/blob/e907dee1b2a52c023210e5e23be95c6f08fa16f1/world_core/romance/engine.py) 提供亲密关系状态、事件增量和范围钳制的对照实现；其恋爱事件阈值和固定奖励属于上游游戏设定，不是本产品的默认规则。

**建议**：心情与长期好感分开。模型可以提出带原因的变化候选，程序校验幅度、来源和事件去重；向基线变化以游戏时长为准。鉴定读取已保存值，而不是每次鉴定再请求模型。不能照搬 Ashley 的长期忽略惩罚，把用户正常睡觉/离开 App 自动当作伤害关系。

**验证**：同事件重复处理不重复加减；休息不会凭空扣好感；高好感仍受忙闲限制；重新生成措辞不会自动刷分；初始关系能符合卡设定。数值范围、情绪维度、更新算法仍需设计/产品确认，不声称这些开源模型有心理学测量效度。

对照排除：[Affinity Agent 项目说明](https://github.com/maniac8/galgame-emotion-agent/blob/642edf8dfcc540b649260a5c662c8d06238a9f3f/README.md) 描述了日程、关系和主动联系愿景，但核验提交的完整文件树仅 `.gitignore` 与 `README.md`，无实现及许可证文件。不能当作可直接复用的开源引擎，也不搬其中内容作为代码资产。

### 3.9 入场背景、此时此刻、前尘往事与鉴定

[Generative Agents 日程与背景更新源码](https://github.com/joonspk-research/generative_agents/blob/fe05a71d3e4ed7d10bf68aa4eda6dd995ec070f4/reverie/backend_server/persona/cognitive_modules/plan.py) 的 `revise_identity` 从近事更新 `currently` 描述，为“当前处境可变、原始人物设定保留”提供具体参照。但它有多次模型请求，不能直接复制其整段日更新流程。

**建议**：角色原始设定、入场适配结果、当前简述、已发生经历分开；先用当前世界事实和角色核心设定生成入场候选，再校验地点/时间/知情范围。相关事件变化才重写“此时此刻”，每次打开资料或鉴定只读取，不额外生成。

“前尘往事”是否追加后续重要经历尚待确认；可以沿用带来源的事件摘要，但不要为此提前建设通用图数据库或全量向量记忆服务。鉴定为原生 Compose 只读页面即可，无需独立 Agent 框架。

**验证**：导入预览与正式入场一致；旧背景生成迟到不能覆盖新世界状态；普通资料页不出现“此时此刻”栏目；鉴定与地图/日程一致；私人事件不进入不知情角色的背景。

### 3.10 可变世界书

[Lorebook Extender 更新与版本源码](https://github.com/EddieMayhem/ST_lorebook_extender/blob/0ed9e8ec5df73d74a1ee0adb26b574a353a854f9/index.js) 有按聊天快照取增量、调用模型生成更新书、规范化 JSON、保存带时间戳的新版本及清理旧版本的流程。它支持比较变更，但不是“只许改某些字段”的完整实现；整书生成会扩大误改面，自动清理版本也不是本项目已授权行为。

[StatefulLore 状态、重生成与脚本加载源码](https://github.com/cgstever/StatefulLore/blob/b03dac39fd82d75bc1a3f17f4f0b23e956838946/core.js) 提供按消息/备选回复保存状态、读取时克隆快照，以及处理重生成状态串改的具体经验。源码会通过 Blob URL 动态导入 lore JavaScript，并依赖 SillyTavern 的提示拦截/宿主。这里仅参考状态快照和去重边界，不把任意可执行世界书模块接入 Momoly。README 所述存储概况不能代替当前消息状态源码。

[RFC 6902](https://datatracker.ietf.org/doc/html/rfc6902) 定义 JSON Patch 操作及 `test` 检查，可用于表达条件更新，但协议本身不保证事实正确、权限正确或跨文件/数据库事务安全。

**建议**：固定原文保留，可变状态形成带版本的覆盖层。输入事件与目标版本→只输出允许路径上的变更→校验编号/类型/范围/知情边界→一次性提交并记原因。版本变化时旧更新不能直接落入新状态。若只实现受限操作集，应称“项目变更格式”或“JSON Patch 子集”，不声称完整标准兼容。

动态修改与再次导入合并分开：导入不能覆盖世界已经发生的变化。地图可以改变允许的地点状态，不能通过任意 patch 自动新增地点，绕过后续阶段边界。

**验证**：不可变字段修改被拒、错误路径被拒、版本过期被拒、重复事件无叠加、生成失败无半更新、私密信息不泄漏、重生成/删消息策略明确后再验收。

### 3.11 消息游戏时间与五分钟标记

现有 `ConversationOps.nextTs` 用严格递增的现实时间值保证消息标识；`ChatMessage.dataJson` 镜像当前 `alts` 的版本状态，不能假定它是独立、不可变的通用元数据槽。见本地证据表。

**建议**：把游戏发生时间、世界编号、稳定事件编号与真实存储标识分开。可以评估显式字段或独立元数据，但先验证消息切换版本、重生成、搜索、分段和删除的语义；不为避免表变化而把字段盲塞进 dataJson。用户已取消旧数据兼容，仍要遵守本项目消息不变量与正常持久化。

显示规则按同会话相邻消息的游戏发生时间计算，`>= 5 分钟` 显示；首条和跨日独立处理。模型只负责正文，不负责生成可信时间戳。

**验证**：4:59/5:00/5:01、同刻多气泡、跨日、休息补齐、多角色切换、备选回复切换、用户新消息与历史补齐交错。重开补齐的历史留言必须在新用户输入之前如何展示/排序，需要设计明确，不能简单按网络返回先后拼接。

### 3.12 持久化与验证工具

[kotlinx-coroutines-test](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-test/) 提供虚拟调度时间与可控延迟；它是测试工具，不是产品游戏时钟。配合注入的世界时钟、假模型可验证离线/快进与失败恢复，无须等真实几小时。

[Android 生命周期文档](https://developer.android.com/topic/libraries/architecture/lifecycle) 可用于界面进入/离开时连接状态，但不能只在页面退出或 `onStop` 时保存关键世界进度。消息与世界状态若分库存放，需明确跨存储提交和重试；文件互斥锁本身不保证崩溃后的整体一致。

本轮仅检查文档，不增加镜像实现的测试。未来自动化需验证行为与故障，不验证“代码是否照自己写法运行”；最终仍需要真实模型和真机证明用户看见的效果。

## 6. 推荐组合与不采用项

**推荐进入详细设计的组合**：现有 Compose 界面 + 自建小型 Kotlin 时间/事件协调 + Generative Agents 的时间段计划思想 + Ashley 的事件/状态分离思想 + 受限动态条目更新 + 现有模型生成与会话存储。优先零新增运行依赖；Schema 校验库作为备选，地图需要大底图时再评估 MapCompose。

| 不采用或暂缓 | 原因 |
| --- | --- |
| AI Town 的 Convex 服务端和 60Hz 模拟整体搬入 | Android 本地补算不需要常驻服务端或像素移动循环 |
| Generative Agents 每层活动都请求模型 | 长休息/多角色成本和等待会放大；借机制、不复制调用密度 |
| Idle 插件的浏览器计时器与伪用户触发路径 | 不符合游戏时间、跨页面/重启与真实历史规则 |
| 统一低日限额、未回复就永不再联系 | 与用户允许休息期间多轮留言不符；控制重复不等于砍掉需求 |
| Ashley 的忽略惩罚、BRING 恋爱阈值 | 是上游产品选择，不是用户确认的好感规则 |
| StatefulLore 的动态可执行脚本 | 与本阶段数据条目更新需求不匹配，不能直接移植浏览器宿主 |
| 整本世界书直接重写/自动删除旧版本 | 误改固定设定、丢追溯；采用受限变更并单独设计保留策略 |
| Cataclysm-DDA 天气代码直接移植 | C++ 与重型模拟不适配，许可/素材不能一并套用 |
| Affinity Agent 作为现成引擎 | 核验提交只有说明文件，无实现/许可证 |
| WorkManager、通知、前台服务、现实天气服务 | 本阶段后台通知明确不做；模拟天气来源尚待确认 |

## 7. 开工前仍需处理的缺口

1. **产品选择**：天气来源与粒度、好感/心情显示及范围、前尘往事追加、可变条目标记。它们在需求末节维护，本报告不擅自拍板。
2. **输入合同**：地图/初始信息的专用格式、用户初始位置来源、同世界图合并，给出合法/缺失/冲突样例。
3. **成本与等待**：长离线如何分批、模型生成预算与失败恢复，不能静默截断世界时间或已发生留言。需要实际模型测量，当前没有费用/延迟数值。
4. **因果与一致性**：同刻事件顺序、后台补齐期间用户输入、世界切换与迟到结果、重生成/删除是否改世界。
5. **平台与库验证**：MapCompose/Schema 库若采用才做最小构建；当前不能报告 Android 集成通过。
6. **体验验收**：真实角色/模型验证忙碌简短回复、空闲跟进、多轮主动留言、动态背景不穿帮；自动测试不证明角色有真人般体验。
