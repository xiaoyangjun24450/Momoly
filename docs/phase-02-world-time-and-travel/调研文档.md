## 1. 结论摘要

1. **Android 端不能照搬常驻模拟**：旧调研与参考项目中的“后台 tick / 常驻进程推进世界”在 Android 上不可依赖；游戏时间应以“用户显式推进 + 打开/回前台结算”为主，比例与补算规则待确认。
2. **时间、位置、行程、日程必须结构化保存**，不能只存在聊天记录或模型上下文中（旧调研已有同类结论，本阶段直接沿用）。
3. **移动是“状态机 + 世界书耗时”**，不是传送；耗时只能来自世界书。但现有世界书引擎只做文本注入，没有结构化地点/路线字段，转换方案是阶段 2 最大的调研缺口。
4. **日程建模有成熟参照**：Generative Agents 的日→时→分计划与重规划、BRING 的 Director/日程 beat；两者都基于常驻模拟，Android 需改为“推进时结算”。
5. **忙闲回复**由需求已确认（不能默认即时回复）；旧调研的防打扰机制可类比，但“忙碌等待策略、待回复上限、过期处理”无现成证据，属待调研。
6. **后台只能保证通知到达**：阶段 2 的最小验证目标是有证据地选定一条路径，并分场景记录后台、锁屏、划掉任务列表、系统强制停止的实际结果，不承诺准时。
7. **旧调研方案与当前计划存在系统性差异**（好友 Store、主动设置、WorkManager、出门场景、备份 v5 均围绕旧需求整体设计），差异与取舍见 §4，冲突以当前需求为准。
8. 本轮是文档整理，未重新联网核验外部资料；沿用 2026-10-31 旧调研的核验记录，未核验边界见 §7。

## 3. 关键机制与证据

### 3.1 世界时间与推进方式

| 参考 | 做法 | 证据来源 | 对 Android 的适配 |
| --- | --- | --- | --- |
| BRING Director | 后台 tick：60 秒现实 ≈ 30 分钟剧情时间，推进反派/随机事件/日程 beat | 旧调研 notes/03、调研报告 §3.4 | 需要常驻调度，Android 不可靠；改为“推进时按时间片结算” |
| AI Town | 全局模拟引擎 + cron，窗口空闲 5 分钟暂停模拟 | 旧调研 notes/03 | 与“不常驻”方向一致：用户离开即停止推进 |
| Generative Agents | 日计划→小时→分钟分解，被打断后重规划 | 旧调研 notes/03 | 分层计划可用于生成日程；每次推进都调模型成本高，宜一次性生成日程后本地求值 |
| Extension-Idle / Time-Awareness | 前台空闲计时 / 页面打开才有效的定时器 | 旧调研 notes/03 | 证明“页面/进程不在就没有计时”，不能作为后台时间依据 |

推进方案候选与证据映射：

| 方案 | 支撑证据 | 缺点 | 现状 |
| --- | --- | --- | --- |
| A 纯手动推进（用户点“推进 10/30 分钟”） | 与 Android 不常驻事实一致；验收可重复 | 世界不会自己走，陪伴感弱 | 待需求方确认（设计建议先做 A） |
| B 现实时间等比映射 + 回前台补算 | 参考 EchoText 服务端“回页面补触发”、旧调研回前台补发结论 | 比例、补算上限、跨世界结算规则都要定 | 待调研 |
| C 常驻 tick（前台服务/WorkManager 周期） | BRING/AI Town 的桌面实现 | Doze/ROM/耗电/政策；周期最小约 15 分钟且不保证准时 | 不建议，阶段 2 不采用 |

说明：以上是机制对照与设计建议，不是已确认的产品规则；“未手动加速时的推进方式”仍需需求方拍板（见 §6）。

### 3.2 地点与出行耗时

| 事实 | 证据 | 含义 |
| --- | --- | --- |
| 世界书引擎只决定“注入哪些文本” | `CLAUDE.md` 世界书边界（constant/关键词/递归/inclusion group/定时效果）；旧调研 §1.5 | 现有能力不能直接产出地点列表与路线耗时 |
| 世界书条目字段是触发/内容语义 | Character Card V2/V3 的字段清单（调研报告 §2A）与现有激活引擎（`CLAUDE.md`） | 没有现成“地点/路线/耗时”标准字段，需要自定义约定 |
| 结构化地点是可行方向 | BRING 的分层实体（角色/地点/事件/规则）、AI Town 的地图/地点 | 值得采用“程序侧结构化模型”，问题只在“数据从哪来” |

数据来源三候选与证据：

| 候选 | 说明 | 证据/风险 | 倾向 |
| --- | --- | --- | --- |
| A 条目正文约定解析 | 从世界书条目正文提取“家到教室步行 20 分钟” | 无标准格式，同义表述会漏解析；但零扩展、作者可直接写 | 仅作兜底 |
| B ST 扩展字段 | 在条目 `extensions` 等位置写结构化路线 JSON | 需保证导入导出原样保留未知字段（本项目已按此实现）；缺生态先例 | 重点评估 |
| C 独立地点库 | 程序侧维护地点/路线库（旧 design/01 的内置 + 自定义方案） | 与当前需求“地点与耗时来自世界书”冲突；仅作历史方案 | 不采用（除非需求变更） |

结论：“地点与耗时来自世界书”是已确认产品规则；但世界书目前没有对应结构，B 是当前最可能兼顾“作者可写 + 程序可读”的方向，需在开工前用验收世界书做一次可行性验证。

### 3.3 角色日程与忙闲回复

- **日程分层有成熟参照**：Generative Agents 的“日计划→小时→分钟”与“被事件打断后重规划”说明日程可以用显式结构表达；BRING 用 Director + schedule beat 把日程变成可调度事件。两者都默认世界持续运行，Android 需改为“读日程 + 按游戏时间求值 + 推进到边界时结算”。
- **日程来源没有现成标准**：角色卡 V2/V3 规范中没有作息/日程字段（调研报告 §2A 的卡字段清单；旧调研 notes/01 本轮未逐篇复核）；需求也明确“不预先要求角色卡包含指定作息字段”。候选来源：角色卡 `extensions`、世界书地点条目中的开放时间、内置模板、验收样例，均需调研后定。
- **忙闲影响回复**由需求确认（日程影响能否见面、何时回复，不能默认即时回复）。旧调研 §3.3 的“防打扰四件套”（频率上限/等待回复时禁止/用户活动重置/总开关）可作为类比：忙时暂不回复、空闲再处理；但“暂缓多久、待回复消息上限、过期处理”没有外部证据，属待调研。
- **一致性要求**：同一角色的位置/日程/互动不得冲突（需求 §2.5）；这是数据建模约束，不是性能优化，必须在模型层保证。

### 3.4 后台通知与执行

| 方案 | 证据 | 适用性 | 结论 |
| --- | --- | --- | --- |
| 回前台补发（App 内 tick + `ProcessLifecycleOwner`） | 旧调研 §3.3；调研报告 §3.3 | 零新系统依赖、省电；不保证锁屏准时 | 可作基础能力，但不能单独满足“关闭 APP 收到通知” |
| WorkManager 周期/一次性任务 | 旧调研 §3.3、设计说明 §3.2 | 周期最小约 15 分钟、不保证准时；Doze/ROM 会延后；重启恢复 | 阶段 2 最小验证的重点候选 |
| AlarmManager + 精确闹钟 | 旧调研 §3.3；Tasks.org/Loop Habit 的重排实践 | 可准点；Android 12+ 需 `SCHEDULE_EXACT_ALARM` 授权；政策需核验 | 需与需求方确认是否接受权限引导 |
| 前台服务（FGS） | 旧调研 §3.3 | 常驻通知打扰；FGS 类型与商店政策未核验 | 不建议首版 |
| FCM/厂商推送 | 旧调研 §3.3 | 准点但需服务端，与“本地优先”冲突 | 不采用 |

平台事实（来源：旧调研对 Android 文档的归纳，本轮未重核验）：`POST_NOTIFICATIONS` 在 API 33+ 需要运行时授权；Doze 与国产 ROM 会延后或阻止后台任务；系统强制停止（Force stop）后闹钟/后台任务通常失效；开机、应用更新、时间变更、精确闹钟权限变化都需要重排任务（Tasks.org 的重排矩阵）。

结论：阶段 2 的最小验证至少覆盖“退到后台、锁屏、划掉任务列表、系统强制停止”四类场景；能证明哪条路径可用，就把它写进阶段 4 的输入，不能把“重新打开 APP 后补发”记成关闭期间通知到达。

## 4. 历史方案与差异

旧调研（2026-10-31）围绕“微信化 + 主动消息 + 出门”整体设计，当前已被五阶段计划拆分。以下差异均以当前需求为准。

| 议题 | 旧调研方案 | 当前计划（2026-11-04） | 处理 |
| --- | --- | --- | --- |
| 好友/关系数据 | `FriendStore`（charFile 为 key，含未读/置顶/免打扰/主动状态） | 通讯录与唯一会话属阶段 1；阶段 2 不建好友 Store | 仅参考其 Store/JSON 持久化模式 |
| 主动消息配置 | `ProactiveSettingsStore`（频率档位/免打扰/每日上限） | 属阶段 4；阶段 2 只验证后台路径 | 阶段 2 不实现 |
| 后台执行 | MVP 回前台补发，P1 上 WorkManager 周期任务 | 阶段 2 只做最小验证，阶段 4 定稿运行方式 | 不预先引入依赖；以实测记录为准 |
| 出门场景 | `OutingPlan`/`SceneState`/`Beat`/`OutingSummary` + `:data:scene` JSON | 赴约与线下故事属阶段 3；阶段 2 只有用户 `Trip` | 阶段 2 不建场景存储与邀约卡 |
| 地点来源 | 内置地点库（asset `places.json`）+ 自定义地点 | 地点与移动耗时来自世界书；阶段 5 由 agent 生成新地点 | 旧“内置库”方案不采用，仅作历史参考 |
| 角色生活状态 | `FriendStore.life`（心情/能量/好感/`scheduleJson`，P2 预留） | 不引入好感数值系统；日程独立建模 | `life` 方案不采用 |
| 游戏时间与跨世界冻结 | 旧方案与 design/01 基本未覆盖（按“好友会话”组织，无世界运行状态） | 当前需求新增：唯一运行世界、游戏时间、冻结/恢复 | 本阶段新增调研与设计，无现成依据 |
| 消息类型与未读 | `dataJson.momoly` 约定、未读口径、邀约卡/系统消息 | 属阶段 1/4；阶段 2 只要求世界状态约束消息 | 阶段 2 不改消息 schema |
| 备份 | `FORMAT_VERSION` 4→5，新增 `RELATIONS`/`SCENES` section | 已取消独立备份/恢复/迁移模块 | 阶段 2 不扩展备份；世界进度不随备份迁移，属已知限制 |
| 出门的定位 | “有状态的场景会话”，独立于聊天 | 与当前阶段划分不冲突（阶段 3 承接） | 沿用“状态显式存储”的结论 |
| 主动/时间注入 | Extension-Idle、EchoText、Time-Awareness 等范式 | 属阶段 4（主动联系）；时间注入可用于阶段 3/4 的 prompt 扩展 | 阶段 2 只展示状态，不注入模型 |

可直接沿用、与当前需求不冲突的旧结论：

1. 时间/地点/约定必须是结构化数据，不能只存在聊天记录里。
2. 地点不能让模型每次现编，否则前后不一致。
3. Android 后台只能保证“通知到达”，生成与结算放回前台；“关闭 APP”要分场景定义。
4. 消息 `ts` 是主键且会话内严格递增，后台/前台并发写需要有互斥与幂等。
5. 新数据不写进角色卡 JSON，避免污染 SillyTavern 导入导出兼容。

旧调研待拍板项的状态变化：世界直接快穿、移动耗时来自世界书、日程影响见面与回复、关闭 APP 只收当前世界通知——已由当前需求确认；时间推进规则、日程来源/格式、后台运行方式——仍待调研（见 §6）。

## 7. 参考链接与核验说明

**本轮核验范围**：仅阅读工作区文档与源码（未联网）。以下两类结论分开标注。

本轮直接核验的源码事实：

- `:core:model` 的 `data/world/WorldContext.kt` 已有 `WorldContext`/`WorldContextProvider` 与 `PlaceholderWorldContextProvider`（`isPlaceholder=true`，固定“家/08:00”）；`ChatContent` 当前直接使用占位 provider。
- 世界目前是 UI 层按世界书名的分组（`HomeWorldSelection`/`HomeScreen`），没有独立世界状态存储。
- 消息时间戳由 `ConversationOps.nextTs` 取现实毫秒（`max(System.currentTimeMillis(), 末条 ts + 1)`），与游戏时间无关联。
- 全仓无 `Notification`/`WorkManager`/`AlarmManager`/`POST_NOTIFICATIONS`/`onNewIntent` 相关实现，通知与后台需从零新增。
- 依赖方向与 import 黑名单由根任务 `checkArchitecture` 强制（`allowedLayers` + 目录规则）。

沿用 2026-10-31 旧调研、本轮未重核验的外部事实：

- 参考项目存在性、许可（GitHub API / raw README/LICENSE / shields 徽章）；SillyTavern 群聊与 STscript 文档；Yarn Spinner saliency 官方博文；Ren'Py 许可页；Momoly 自身 AGPL-3.0。
- 明确未核验：`targetSdk 37` 的通知/精确闹钟/FGS 具体政策；Doze 与国产 ROM 实际行为；WorkManager 默认进程模型；SillyTavern 生态是否存在“地点/路线”约定先例；Time-Awareness 的许可（仓库无 LICENSE）；旧调研之外的新项目未覆盖。
