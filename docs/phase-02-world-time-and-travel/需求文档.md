## 1. 阶段目标与可体验结果

一句话目标：让世界和角色拥有可观察的时间、位置与活动——用户能切换世界、选择推进的时长、选择出行方式，并在路上继续聊天。

| 目标 | 完成后可实际看到 |
| --- | --- |
| 世界可运行、可冻结 | 世界选择页；当前世界名与游戏时间；其他世界显示冻结且时间不变 |
| 游戏时间可推进 | 用户选择推进时长（如 10 / 30 游戏分钟），当前世界进度前进，其他世界不动 |
| 地点与出行可读取 | 当前世界地点列表；选择目标地点后显示可用出行方式与耗时 |
| 出行有过程 | “路上/前往某处中”状态、剩余时间；累计消耗足够游戏时间后才到达 |
| 途中可聊天 | 路上仍能收发消息，行程不被聊天改变或提前结束 |
| 角色有日程 | 角色当前地点、活动状态（忙碌/移动/空闲）随游戏时间变化 |
| 回复受状态约束 | 角色忙碌时暂缓回复，空闲后处理待回复消息，不重复发送 |
| 后台路径可验证 | 目标设备收到真实测试通知，各运行场景有分别记录的实际结果 |

本阶段只交付“世界时间 + 用户出行 + 角色日程 + 后台最小验证”。赴约与线下故事在阶段 3；主动联系、正式通知与通知跳转在阶段 4；agent 生成新地点在阶段 5。

## 3. 功能需求

### 3.1 可运行的地点与出行设定（模块 2）

| 项 | 要求 |
| --- | --- |
| 输入 | 已合并的世界书，含地点、场景、路线、出行方式与耗时信息 |
| 输出 | 该世界的地点列表，以及可供出行读取的路线、方式、耗时数据 |
| 来源 | 移动耗时以世界书为来源，不得按现实秒数或距离自行估算 |
| 表达方式 | 具体字段与读取方式待调研（见 §7），不预先锁定结构 |
| 例子 | 世界书写明“家到教室步行 20 分钟、骑行 8 分钟”，地点页选择教室后显示这两种方式与耗时 |

数据缺失时不能编造耗时：应给出可理解的失败或不可用状态，并保留用例记录。后续阶段 5 新增地点沿用同一呈现结构。

### 3.2 世界运行、游戏时间与冻结（模块 3）

- 同一时间只有一个世界运行；运行世界的游戏时间、用户行程、角色日程随推进变化。
- 世界之间直接切换（快穿），无需出行等待；切换即冻结原世界、恢复目标世界，本次切换不消耗游戏时间。
- 时间推进只作用于当前世界；其他世界的时间、日程、移动与回复全部暂停，也不会主动发消息。
- 返回原世界时从离开时的冻结时间与状态继续，保留位置、行程、日程与进度。
- 游戏时间与消息实际收发时间分别保存：聊天列表/消息排序仍按真实收发时间，游戏时间独立记录用于世界展示与规则判定。
- 本阶段必须确定两件事，并写进验收记录：未手动加速时的游戏时间推进方式；一次推进跨过多个到期事件（到达、日程切换等）时的处理顺序。
- 聊天发送与回复入口遵守世界状态：冻结世界不能产生新消息或新回复。

| 操作 | 应看到的结果 |
| --- | --- |
| 校园世界 08:00 推进 30 分钟 | 校园 08:30，奇幻仍为 10:00 并显示冻结 |
| 切到奇幻推进 10 分钟再返回校园 | 奇幻 10:10；校园仍为 08:30，状态从冻结点继续 |

### 3.3 用户出行与途中聊天（模块 4、6）

- 用户从当前地点出发，选择目标地点与出行方式；所需时间来自世界书对应路线与方式。
- 出发后进入“路上”状态并显示剩余时间；必须累计消耗足够游戏时间才能到达，不能瞬时到达或提前到达。
- 用户可以选择本次推进的时长（如 10 分钟）；推进量同时作用于行程与当前世界其他状态。
- 路上保留聊天入口：可以收发消息；角色是否回复仍由世界与角色状态决定，聊天不改变行程计时、不导致直接到达。
- 到达后位置更新为目标地点，行程结束；可再次发起出行。
- 出行中途切换世界，行程暂停；返回后从冻结进度继续（见 P2-10）。

### 3.4 角色日程、位置与回复时机（模块 5、6）

- 当前世界角色按自己的日程移动与活动，位置和活动状态随游戏时间变化；其他世界角色保持冻结。
- 角色移动也遵守地点之间的耗时，日程中的“移动段”必须消耗对应时间。
- 角色忙碌时暂缓回复；进入空闲时段后处理此前待回复的消息，且不重复发送。
- 世界冻结时，角色日程、移动与回复全部暂停。
- 角色位置、日程与正在进行的互动保持一致，避免同一角色同时出现在互相冲突的场景中。
- 日程信息作为阶段 3 赴约与阶段 4 主动联系的基础，本阶段只保证可读取、可推进、可展示。
- 初始地点与日程的来源、格式待调研；验收使用总计划的可重复日程，不要求角色卡自带指定作息字段。

验收日程（与总计划一致）：林夏 08:00—08:30 在教室忙碌，08:30—08:40 步行前往图书馆，08:40—10:00 在图书馆空闲；沈言 08:00—10:00 位于图书馆；周宁在家。校园世界初始 08:00，奇幻世界初始 10:00，各自保存游戏时间。

### 3.5 后台通知最小验证（模块 12）

- 用一个确定会到期的测试任务，验证后台执行与通知路径，不接入完整的角色主动联系策略。
- 必须收到真实系统通知，而不是只在本应用内显示提示。
- 场景分别记录：退到后台、锁屏、划掉任务列表。系统强制停止作为独立场景记录，不能与普通关闭混为一谈。
- 只证明技术路径可行，不代表角色主动联系已完成；阶段 4 采用本阶段验证出的运行路径。

## 4. 跨模块约束

| 约束 | 说明 | 验收影响 |
| --- | --- | --- |
| 唯一运行世界 | 任意时刻只有一个世界在运行，其余全部冻结 | P2-02、P2-03、P2-10 |
| 冻结始终适用 | 不只在用户进行线下互动时冻结；任何离开当前世界的状态都冻结 | P2-02、P2-09、P2-10 |
| 快穿不耗时 | 世界切换不产生游戏时间消耗，不受移动耗时规则限制 | P2-03 |
| 移动耗时只来自世界书 | 不得用真实秒数、距离或固定表替代世界书设定 | P2-01、P2-04、P2-05 |
| 游戏时间与消息时间分开保存 | 消息时间戳继续表示真实收发时间；游戏时间独立记录，两者不互相推导 | P2-11 及全部用例 |
| 状态来源唯一 | 首页、聊天顶栏、世界页显示的世界时间与位置必须来自同一世界状态；阶段 1 的固定占位由真实状态替换 | P2-02、P2-11 |
| 角色状态一致 | 同一角色的位置、日程、活动、行程不互相冲突 | P2-07、P2-09 |
| 线上只发消息正文 | 阶段 1 已确认的纯消息规则在途中聊天继续适用，不因出行改变 | P2-06 |
| 验收素材可重复 | 使用总计划的校园 08:00、奇幻 10:00、路线表与日程；从可复现起始状态开始 | 全部用例 |
| 不新增备份/迁移模块 | 世界进度、行程、日程作为业务数据随功能记录，正常重新进入保持连续 | P2-11 |
| 不改变阶段 1 已确认规则 | 通讯录分组、唯一会话、世界归类与导入规则不变 | 阶段 1 回归 |

## 5. 验收用例

准备：使用总计划的世界、路线与日程；精确检查游戏时间时，记录验收所用的自然推进规则，并从可重复的起始状态开始；涉及生成内容的用例连接实际配置的模型服务。

| 编号 | 操作步骤 | 应看到的结果与通过标准 |
| --- | --- | --- |
| P2-01 | 进入校园世界，查看地点和出行方式。 | 家、教室、图书馆可见；对应方式和耗时与世界书一致。 |
| P2-02 | 在校园世界推进 30 游戏分钟，查看两个世界的时间。 | 校园推进到对应时间；奇幻仍停在原时间并显示冻结。 |
| P2-03 | 切换到奇幻世界并推进时间，再返回校园世界。 | 切换无需出行等待；校园从冻结点继续，角色状态也从保存位置继续。 |
| P2-04 | 在家选择步行去教室，先推进 10 分钟，再推进剩余时间。 | 途中显示路上和剩余时间；累计消耗 20 游戏分钟后到达，不能提前变成在教室。 |
| P2-05 | 从相同起点选择骑行路线。 | 显示并使用世界书给出的 8 分钟耗时；不同方式实际影响出行时间。 |
| P2-06 | 用户在路上时与空闲的沈言聊天。 | 可以收发消息；出行状态保持正确，不因聊天直接到达或重新计时。 |
| P2-07 | 分别推进到林夏的忙碌、移动和空闲时段。 | 依次显示教室忙碌、前往图书馆、在图书馆空闲；位置变化符合路线耗时。 |
| P2-08 | 忙碌时给林夏发消息，再推进到可回复时段。 | 用户消息保存；角色不绕过忙闲规则即时回复；空闲后能处理待回复消息，且不重复发送。 |
| P2-09 | 让角色开始生成回复，随后切换世界。 | 原世界冻结后，未完成生成不能继续作为该世界的新消息提交或通知；返回后按保存状态和调度规则继续。 |
| P2-10 | 用户移动中切换世界，在另一个世界推进时间，再返回。 | 原世界的用户行程和角色日程未偷跑，从冻结进度继续。 |
| P2-11 | 保存移动状态，关闭并重新打开 APP。 | 当前世界、位置、移动进度和角色状态按已确定的时间规则恢复；冻结世界不推进。 |
| P2-12 | 在目标设备执行最小后台通知验证。 | 能展示真实系统通知；各运行场景分别留有实际结果；明确阶段 4 可采用的运行路径及待解决差异。 |

通过条件：当前世界的时间、用户出行和角色活动一致，其他世界全部冻结；后台通知具有已验证的实现路径。任一用例未执行或未通过，不得标记阶段完成。此外必须回归阶段 1 的关键路径。

| 跨日与日期显示 | 游戏时间只显示 HH:mm 还是含日期，跨日如何表示 | 阶段 2 |
| 游戏时间是否注入聊天上下文 | 阶段 1 占位值明确不注入模型；替换为真实状态后是否注入、以什么形式注入 | 阶段 2 末或阶段 3 前 |
| 待回复消息保留规则 | 忙碌期间累计待回复消息是否设上限、过期如何处理 | 阶段 2 |
